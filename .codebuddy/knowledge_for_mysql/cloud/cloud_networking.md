## 概述

### 是什么

云上网络 = **多层级 IP 地址 + 多类型网关 + 多类服务模式（Overlay/Underlay）** 的复合体系。要理解云数据库的网络访问，必须先理解这张网。

### 用途

- 把"私网"和"公网"两套地址空间安全打通
- 在不暴露物理 IP 的前提下，让客户端用一个稳定地址（VIP/ClusterIP）访问动态变化的物理节点
- 把不同网络（VPC、K8s、公网）隔离/桥接，安全可控

### 服务模型定位

云上网络 = **IaaS 层**的关键组成（虚机/网络/存储三大件之一），与 PaaS（云数据库）和 SaaS 形成完整栈。

## 理论基础

### 设计模式

| 模式 | 体现 |
|------|------|
| **分层（OSI 7 层）** | L3 网络层/L4 传输层/L7 应用层 各自独立设备和职责 |
| **代理模式** | Proxy/LB 作为中间层，客户端只看到 VIP |
| **地址抽象** | VIP/ClusterIP/Pod IP 都是抽象层，屏蔽物理细节 |
| **命名空间隔离** | VPC（租户级）、Pod（容器级）、netns（内核级）逐层隔离 |
| **封装/解封装** | VXLAN 把内层 Pod 网络封装在外层物理网络中 |

### 相关论文/标准

- **RFC 1918**：私网地址段（10/8、172.16/12、192.168/16）
- **RFC 7348**：VXLAN 标准
- **Linux Bridge / Veth pair**：容器网络的基础
- **iptables / ipvs**：Linux 内核流量转发机制

### 算法与数据结构

- **iptables**：规则链式匹配（O(n)，5-tuple match）
- **ipvs**：哈希表（O(1)，更适合大规模 Service）
- **路由表最长前缀匹配**：IP 路由查找基础算法
- **NAT 表**：五元组映射（src_ip:port ↔ dst_ip:port）

### 类似实现对比

| 维度 | 腾讯云 | AWS | 阿里云 |
|------|--------|-----|--------|
| 私有网络 | VPC | VPC | VPC |
| 基础网络 | 基础网络（淘汰）| EC2-Classic（淘汰）| 经典网络（淘汰） |
| L4 LB | CLB（四层底层为内部 TGW） | NLB | SLB |
| 跨账号打通 | PrivateLink | PrivateLink | CEN |
| K8s | TKE | EKS | ACK |

### 历史背景

早期云厂商把 CVM 放在"基础网络"——所有租户共享一个大内网，靠安全组隔离。**太弱**，租户能扫到别人 IP。于是引入 VPC，每个租户一个独立网络空间。基础网络逐步淘汰。

## VPC / 子网 / 网段

### VPC 不是子网

**VPC 是包含子网的私有网络空间**，子网是 VPC 内的 IP 段切分：

```
VPC: 10.0.0.0/16（私有网段）
├── Subnet-A: 10.0.1.0/24（可用区1）
│     ├── CVM-A1: 10.0.1.10
│     └── CVM-A2: 10.0.1.11
├── Subnet-B: 10.0.2.0/24（可用区2）
│     └── CVM-B1: 10.0.2.10
├── 路由表（VPC 级别）
├── 安全组（VPC 级别）
└── NAT 网关 / VPN / 对等连接
```

### VPC 网段必须是私网 IP

RFC 1918 规定的私网段：

| 段 | 范围 | 常用度 |
|----|------|--------|
| `10.0.0.0/8` | 10.0.0.0 ~ 10.255.255.255（A 类） | **最常用**，云数据库默认 |
| `172.16.0.0/12` | 172.16.0.0 ~ 172.31.255.255 | 次常用 |
| `192.168.0.0/16` | 192.168.0.0 ~ 192.168.255.255 | 局域网/家用 |

**VPC 不能用公网 IP**（设计上是隔离的私有网络）。

### VPC 创建与收费

- **免费**：VPC 本身、子网、安全组、同地域内网互通
- **收费**：EIP（闲置时也收费）、NAT 网关、VPN 网关、跨地域对等连接（具体价格查官方定价页，随时间调整）

### 何时需要公网 IP（EIP）

| 场景 | 需要 EIP？ |
|------|-----------|
| VPC 内 CVM 互访 | ❌ |
| CVM 主动访问公网（yum/wget） | ⚠️ 需要 NAT SNAT（或 EIP） |
| 外部用户主动连 CVM/数据库 | ✅ 需要 EIP 或 DNAT |
| Web 服务对外 | ✅ 需要 EIP |
| 云数据库默认 | ❌ 默认不暴露，需要时走 Proxy |

### VPC 内子网默认互通（重要澄清）

**VPC 内所有子网默认就是互通的，不需要任何"打通"操作**：

```
VPC 10.0.0.0/16
├── Subnet-A 10.0.1.0/24
└── Subnet-B 10.0.2.0/24
     ↑ 默认互通，无需配置（vpcgw/分布式路由默默转发，用户无感）
```

真正需要**显式操作**的是：
- 出公网：配置 NAT 网关（SNAT 规则）
- 进公网流量：绑定 EIP 或配 DNAT
- 跨 VPC：PrivateLink / 云联网 / 对等连接
- 专线/VPN 接入：申请对应网关

> 注意：不要把"vpcgw 参与子网间路由"误解为"子网间默认不通需要打通"——
> vpcgw 在子网间路由上是**透明的基础设施**（后台默默干活），不是用户需申请的服务。

## 计算资源形态：CVM / 裸金属 / 物理机

**裸金属 ≠ 物理机**：裸金属是云厂商把整机物理服务器独占给你（但你不用买硬件、不用运维机柜），物理机是你自己买自己管。

| 概念 | 本质 | 类比 |
|------|------|------|
| **物理机** | 真实服务器硬件，自己买自己管 | 自己盖的房子 |
| **裸金属（BMS）** | 云上的物理机：整台物理服务器独占，**无虚拟化层**，但接入云管理体系（VPC/镜像/监控） | 整租一栋楼，物业是云厂商 |
| **CVM** | 云虚拟机：跑在共享宿主机上的虚拟机（KVM 等虚拟化切分） | 租楼里的一个房间 |

| 维度 | 物理机（传统 IDC） | 裸金属（云 BMS） | CVM（云虚拟机） |
|------|------------------|------------------|----------------|
| **谁拥有** | 你自己买 | 云厂商独占给你 | 云厂商共享 |
| **物理硬件** | 你的机柜 | 你的物理服务器 | 共享宿主机 |
| **虚拟化层** | 无 | 无 | 有（KVM/Hyper-V） |
| **Hypervisor 损耗** | 0 | 0 | ~3-8% CPU 损耗 |
| **网络控制** | 你自己拉网线 | 云厂商网络（VPC 内） | 云厂商网络（VPC 内） |
| **OS 控制** | 完全自由 | 完全自由 | 完全自由 |
| **存储控制** | 完全自由 | 可加本地 NVMe SSD 直通 | 默认云盘（网络存储） |
| **弹性交付** | 采购数周 | 分钟级 | 秒级 |
| **License 优势** | 无 | 可绑物理硬件（如 Oracle） | 无 |
| **合规/隔离** | 自负责 | 物理隔离（满足等保） | 共享风险 |
| **典型用途** | 自建机房/极致性能 | Oracle/传统应用上云/合规/**数据库 RS** | 绝大多数业务 |

### 裸金属独有优势

- **Oracle 等绑定 CPU socket 的 license**：CVM 会被多算 socket，裸金属按物理 CPU 算
- **本地 NVMe SSD 直通**：避免网络存储延迟，对数据库关键
- **PCI-DSS 等合规**：物理隔离满足监管要求
- **极致网络**：SR-IOV 直通，绕过虚拟化网络层

### 数据库 RS 选型

- TDSQL-C 大多用**专用物理机**（不是 BMS，是云厂商的资产）
- 自建数据库上云用 BMS 跑 Oracle
- 业务部署选 CVM

## EIP（弹性公网 IP）

**Elastic IP（弹性公网 IP）** = 腾讯云的公网 IPv4 地址资源。

| 特性 | 说明 |
|------|------|
| **可独立持有** | 不绑特定 CVM，可自由绑定/解绑到任意实例 |
| **跨实例迁移** | 解绑后绑到另一台，业务秒级恢复 |
| **带宽单独计费** | EIP 本身 + 带宽费 |
| **与普通公网 IP 区别** | 普通公网 IP 创建即绑定 CVM，EIP 可独立 |
| **可释放** | 不用了释放掉省费用 |

### 典型用法

- 给 CVM 配 EIP 提供公网入口
- 给 NAT 网关配 EIP 让私网出公网
- 给数据库开公网入口（DB EIP）
- **防 DDOS**：EIP 可绑定高防 IP 实例

## NAT 与公网访问

### NAT 类型

| 类型 | 用途 | 方向 |
|------|------|------|
| **SNAT（源 NAT）** | 私网机器访问公网 | 私网 → 公网 |
| **DNAT（目的 NAT）** | 公网用户访问私网机器 | 公网 → 私网 |
| **一对一 NAT（弹性 IP）** | 公网 IP 直接绑内网机器 | 双向 |

### 工作原理

```
私网 10.0.1.10:8080  →  NAT 网关  →  公网 139.198.x.x:10080  → 互联网
            │                                          ↑
            └──────── NAT 表映射 (session 跟踪) ────────┘

NAT 表:
  内网 (10.0.1.10:8080) ↔ 公网 (139.198.x.x:10080)
  （同一会话保持映射，响应包按反向映射回原内网机器）
```

### 关键限制与澄清

- **NAT 网关必须绑定 EIP**：SNAT 后的公网出口 IP 就是所绑的 EIP
  - 绑 1 个 EIP → 出口 IP 固定（白名单场景推荐）
  - 绑多个 EIP → 流量在多个 EIP 间轮询（出口不固定，影响白名单）
- **NAT 表耗尽**：并发连接数受 NAT 网关规格限制（550 万~1 亿并发连接，按规格）
- **端口耗尽**：单个 EIP 约 6 万可用端口（TCP 16bit），高并发短连接场景需绑多个 EIP

## VIP / 虚拟 IP

### 本质

**VIP = 不绑定物理网卡的 IP**，由路由规则/网关动态指向当前物理节点。

```
VPC: 10.0.1.0/24
  CVM-1 (10.0.1.10): 绑 eth0
  CVM-2 (10.0.1.11): 绑 eth0
  VIP (10.0.1.100):  ★ 不绑任何网卡
  
  路由表:
    10.0.1.100 → CVM-1（当前主）
```

### VIP 的关键特性

| 特性 | 说明 |
|------|------|
| **不绑物理 NIC** | 在操作系统 `ip addr` 里看不到 |
| **由路由层指向** | TGW/VPCgw/Proxy 维护"VIP 指向哪个 RS" |
| **切换不改 IP** | VIP 本身不变，只改指向的物理节点 |
| **客户端无感知** | 客户端只连 VIP，不需要知道后端 RS |

### VIP 一定是 VPC 内 IP 吗？

**是的，VIP 在 VPC 内**。但严格说是"**有 IP 路由可达的私网 IP**"——不一定非得在 VPC 内，也可以是公网 IP 形式存在（如负载均衡器的公网入口）。

**没 VPC 一定没 VIP？** 不严格。VIP 的本质是"不绑网卡靠路由转发"，任何支持路由转发的网络都能有 VIP，包括：
- 没有 VPC 的传统物理网络（keepalived + VIP 漂移）
- 跨 VPC 的浮动 IP

但在云数据库语境下，VIP **必然**在某个 VPC 内。

### VIP 与 RS 的关系

```
客户端 → VIP → [网关层选择 RS] → 某个 RS 物理 IP

切换时: VIP 不变，改网关层的路由指向，从 RS-1 切到 RS-2
```

## RS / 真实服务器

### RS = Real Server

**RS 是网关/负载均衡后面的真实业务服务器**。

在云数据库语境：

| 角色 | 含义 |
|------|------|
| **VIP** | 数据库访问入口（客户端看到的） |
| **RS** | 实际跑 mysqld 的节点（RW 或 RO） |
| **网关** | TGW / Proxy，负责把 VIP 流量分发给 RS |

### RS 是物理机吗？

**不一定**。可以是：
- 物理机（dbserver 通常用专用机型，如腾讯云 cdb 物理机）
- 虚拟机（CVM）
- 裸金属（专用物理机）
- 容器化部署（K8s Pod）

**腾讯云 TDSQL-C 的 RS**：传统是专用物理机（或带本地 NVMe SSD 的 CVM），跑 mysqld 进程；计算存储分离架构下，存储不在本地。

## L3 / L4 / L7 分层

### OSI 7 层模型

| 层次 | 名称 | 协议/概念 | 设备/组件 |
|------|------|----------|-----------|
| **L3** | 网络层 | IP, ICMP, 路由 | 路由器、VPC gateway |
| **L4** | 传输层 | TCP, UDP, 端口 | L4 LB（TGW）、iptables |
| **L7** | 应用层 | HTTP, MySQL, DNS | 反向代理、Proxy |

### L3 / L4 / L7 网关的功能差异

| 网关 | 看到什么 | 做什么 |
|------|---------|--------|
| **L3 网关** | IP 包头（src/dst IP） | 路由转发、NAT、ACL |
| **L4 网关** | TCP 头（src/dst IP+port） | 端口转发、L4 LB、连接级负载均衡 |
| **L7 网关** | 应用协议内容 | HTTP 路由、MySQL 协议解析、读写分离 |

### 关键：网关不"只"工作在一层

虽然 L4 网关"核心"在 L4，但它要管理 TCP 连接，必然涉及 L3 路由。**主功能在 L4**而非"只在 L4 工作"。

### L4 例子：TGW 的工作

```
客户端 → 139.198.x.x:3306 → TGW（看 TCP 头, 不看 MySQL 内容）
                                    │
                                    ├── RS-1 10.0.1.10:3306（当前主）
                                    └── RS-2 10.0.1.11:3306（备）

TGW 做的事:
  - 接受客户端 TCP 连接
  - 根据健康检查 + 负载均衡选 RS
  - 建立 TGW ↔ RS 的 TCP 连接
  - 透传 TCP 流（不解 MySQL 协议）
  - RS 切换时关旧连、建新连（前端 TCP 必断）
```

### L7 例子：Proxy（理解 MySQL 协议）

```
客户端 → 139.198.x.x:6033（Proxy）→ Proxy（解析 MySQL 协议）
                                       │
                                       ├── 读请求 → RS-RO
                                       └── 写请求 → RS-RW

Proxy 做的事:
  - 解析 MySQL 命令包
  - 读/写分离
  - Session 缓存（变量/PS/schema）
  - 切换时保留前端 TCP，后端重建
  - 可以做读一致性（读 binlog 位点）
```

## 网关体系：腾讯云全量网关清单

### 网关全景表（来自腾讯云内部运维资料）

腾讯云 VPC 平面背后有 **15+ 种网关**，按"作用/实现形态/高可用方案"分类：

| 网关 | 作用 | 实现 | 高可用 |
|------|------|------|--------|
| **pvgw** | vpc0（基础网络）子机和物理网络互通 | 内核无状态 | OSPF |
| **pvgw-dpdk** | 自研 VPC 和自研 IDC 互通 | DPDK 无状态 | OSPF |
| **vpcgw** | 私有网络 **CDB、内网 LB、公共服务、PrivateLink 服务** | 内核有状态 | VRRP |
| **vpcgw-dpdk** | 同上（DPDK 版） | DPDK 有状态 | OSPF |
| **jnsgw** | **物理网络通过 vip:vport 访问私有网络（跳板）** | 内核有状态 | VRRP |
| **mcgw** | 组播、广播 | 内核无状态 | OSPF |
| **natgw / natgw-dpdk** | NAT 网关（私网出公网） | 内核/DPDK 有状态 | VRRP |
| **lbnat** | LB 访问 IDC 的 RS | DPDK 有状态 | VRRP |
| **ccngw** | 云联网跨地域互通、专线 IDC 互通 | DPDK 无状态 | OSPF |
| **pcgw** | 跨地域对等连接 | DPDK 无状态 | OSPF |
| **dcgw** | 专线 IDC 互通 | DPDK 无状态 | OSPF |
| **dcgw-nat** | 专线 IDC 互通（双向 NAT） | DPDK 有状态 | VRRP |
| **xgw** | 裸金属 BMS 与 CVM 互通 | DPDK 无状态 | OSPF |
| **sxgw** | 裸金属 BMS 公网/NAT 网关/LB | DPDK 有状态 | VRRP |

**关键规律**：
- **有状态网关**（需要维护连接/NAT 表）→ 高可用用 **VRRP**（主备，如 vpcgw/jnsgw/natgw）
- **无状态网关**（纯路由/转发）→ 高可用用 **OSPF**（多活，如 pvgw/ccngw/pcgw/dcgw/xgw）
- **内核版 vs DPDK 版**：内核版性能一般、多用于早期；DPDK 版绕过内核、高性能，现网主流
- **TGW** 是公网统一接入网关（前述），与上述 VPC 内部网关是两个层面

### 四个高频网关对比

| 网关 | 层次 | 作用 |
|------|------|------|
| **vpcgw** | L3/L4 | VPC 内 CDB/内网 LB/公共服务/PrivateLink 服务的接入（有状态） |
| **jnsgw** | L3/L4 | 物理网络（含基础网络 vpc0）通过 vip:vport 跳板访问私有网络 VPC（有状态） |
| **TGW** | L4 | 公网/内网统一接入网关（基础设施，对外产品 CLB 的底层） |
| **Proxy（Magpie）** | L7 | MySQL 协议代理：读写分离、连接保持、Session 恢复 |

### 基础网络 vs VPC（本质区别，重要）

**基础网络不是子网，VPC 也不是子网**——两者是平行的网络体系：

```
基础网络（Classic Network，2011-2014 年代方案）:
┌─────────────────────────────────────────┐
│  腾讯云全局共享的大网络（一个大池子）         │
│                                           │
│  用户A的CVM (10.139.1.5)                  │
│  用户B的CVM (10.139.1.6)   ← 所有租户混在  │
│  用户C的CVM (10.139.1.7)     同一个网络里  │
│                                           │
│  隔离手段: 只有安全组（软件防火墙，弱隔离）   │
└─────────────────────────────────────────┘

VPC（2014+ 现代方案）:
用户A的VPC (10.0.0.0/16)      用户B的VPC (172.16.0.0/16)
├── 子网 10.0.1.0/24           ├── 子网 172.16.1.0/24
└── 子网 10.0.2.0/24           └── 子网 172.16.2.0/24
  ↑ 网络层硬隔离，A 永远碰不到 B
```

| 维度 | 基础网络 | VPC |
|------|----------|-----|
| 归属 | 腾讯云全局共享，用户无自己的网络 | 每用户一个私有网络空间 |
| 网段 | 腾讯云统一分配，用户不能自定义 | 用户自定义（RFC1918 任选） |
| 隔离 | 安全组（软件层，弱） | 网络层（强隔离） |
| 子网 | 无概念（扁平） | 有（跨可用区划分） |
| 路由表 | 腾讯云统一管理 | 用户自定义 |
| 自定义网关 | ❌ | ✅ NAT/VPN/专线/对等连接 |
| 互通网关 | **pvgw**（vpc0 子机与物理网络互通） | **vpcgw**（CDB/LB/公共服务/PrivateLink 接入） |
| 现状 | **淘汰中，新用户不可用** | 唯一推荐 |

### "都是一组私网 IP"为什么不能等同（常见疑问）

**VPC ≈ 一组私网 IP，基础网络 ≈ 一组私网 IP，但两者不能等同**——"一组私网 IP"只是表象，本质区别在"**这组 IP 所在的网络平面是共享还是独占**"：

| | 基础网络 | VPC |
|---|---------|-----|
| 类比 | **合租公寓**：一个门牌地址，每人一间房，房门锁（安全组）决定谁能进 | **独栋别墅**：独立门牌，独立围墙，别人根本进不了院子 |
| "一组 IP"的角色 | 每人分一个房间号（IP），但地址（网络平面）是共享的 | 整栋楼（网段）都是你的，地址（网络平面）独占 |

**安全模型完全不同**：
- 基础网络：**默认可达，靠拒绝**（网络层通，安全组一条条挡）
- VPC：**默认不可达，靠放行**（网络层隔离，要通需显式建 PrivateLink/对等连接）

### 更深视角：VPC 本身就是 Overlay

从腾讯云物理网络（underlay）的角度看：

```
物理网络（underlay）: 机房真实网络，腾讯云统一管理
      ↓ 虚拟化（VXLAN/类似技术）
基础网络 = 直接在物理网络上分 IP（扁平，无虚拟化隔离）
VPC      = 在物理网络之上虚拟出的租户私有网络平面（overlay）
```

**VPC 的更准确定义**：在共享物理网络上，用 overlay 技术为你虚拟出来的一个**独占网络平面**，这组私网 IP 只是这个平面的编址。

与 K8s Overlay/Underlay 直接类比：
- 基础网络 ≈ Underlay 思路（直接用物理网络编址）
- VPC ≈ Overlay 思路（物理网络之上虚拟独立网段，靠封装/标签隔离）

**这解释了为什么不同 VPC 可以用相同的网段**（都是 10.0.0.0/16）而互不冲突——就像两个 K8s 集群的 Pod 都用 10.244.0.0/16 不冲突一样，因为它们在**不同的虚拟平面**里。基础网络做不到这点（共享平面，IP 必须全局唯一）。

**基础网络（vpc0）、物理网络、VPC 三者的网关关系**（纠正：jnsgw 不是"基础网络内部网关"）：
- **pvgw**：vpc0（基础网络）子机 ↔ 物理网络 互通
- **jnsgw**：物理网络 → 私有网络（VPC）的**跳板网关**，通过 vip:vport 方式访问（典型场景：自研 IDC/物理网络上的服务访问 VPC 内的 CDB/公共服务）
- **vpcgw**：VPC 内 CDB/内网 LB/公共服务/PrivateLink 服务的接入网关
- 三者职责不同：pvgw 管"基础网络↔物理网络"，jnsgw 管"物理网络→VPC 跳板"，vpcgw 管"VPC 内部服务接入"

### vpcgw 的真实职责

**vpcgw 不做 VPC↔VPC 私网互通**（那是 PrivateLink/云联网/对等连接的事）。它作为**有状态网关**，职责是（据内部运维资料）：

| vpcgw 职责 | 说明 | 用户是否需显式操作 |
|-----------|------|-------------------|
| **VPC 内子网间路由** | 分布式路由默默转发，子网默认互通 | ❌ 无感（不要误解为"需要打通"） |
| **私有网络 CDB 接入** | 云数据库（CDB/TDSQL-C）的内网 VIP 接入 | ❌ 无感（云厂商自动） |
| **内网 LB 接入** | 内网负载均衡的 VIP 接入 | ❌ 无感 |
| **公共服务** | 腾讯云公共服务（如元数据、镜像源） | ❌ 无感 |
| **PrivateLink 服务** | PrivateLink 终端节点服务的转发 | ✅ 需建终端节点/服务 |
| **NAT 出公网** | 由 natgw（NAT 网关）承担，不是 vpcgw | ✅ 需配 NAT 网关 |
| **公网进私网** | 由 EIP + 公网接入（TGW）承担 | ✅ 需绑 EIP |
| **专线/VPN 接入** | 由 dcgw/专线网关承担 | ✅ 需申请专线/VPN 网关 |

> 注：vpcgw 与 natgw/dcgw 是**不同的网关**——vpcgw 管 VPC 内部服务接入，natgw 管出公网 NAT，dcgw 管专线接入。这些网关各司其职，不要混为一谈。

### TGW 的角色

TGW（Tencent Gateway）是**腾讯内部的自研统一接入网关基础设施**（非用户可购买的对外产品）：

```
定位: 公司级流量入口基础设施（微信/QQ/游戏/视频等内部业务都经 TGW 接入）
功能: 4 层负载均衡 + 外网接入 + 多线接入（BGP）+ IP 漂移容灾
实现: DPDK 高性能转发，单集群亿级并发、千万级 PPS
七层: STGW = TGW + nginx + 加解密（HTTPS/QUIC/HTTP3）

与 CLB 的关系:
  CLB（Cloud Load Balancer）= 腾讯云对外的负载均衡产品
  四层 CLB 底层由 TGW 实现；七层 CLB 由 STGW 实现
  用户买的是 CLB，流量实际跑在 TGW 集群上
```

**产品级横向对比**（用户可购买的产品）：腾讯云 CLB ↔ AWS NLB/ALB ↔ 阿里云 SLB。

## 安全组（Security Group）

**腾讯云安全组 = 分布式 iptables 防火墙**，附着在实例（VM/DB）上做入站/出站过滤。

```
┌─────────────────────────────────┐
│ 安全组（绑定到 CVM/DB 实例）      │
│  ┌─ 入站规则（谁可以访问这台机器）│
│  ├─ 出站规则（这台机器能访问谁）  │
│  └─ 默认规则（拒绝/允许）          │
└─────────────────────────────────┘
```

| 维度 | 安全组 | 网络 ACL |
|------|--------|----------|
| **作用层** | 实例级（ENI/网卡） | 子网级（无状态） |
| **粒度** | 精确到实例 | 整段子网 |
| **状态** | 有状态（响应包自动放行） | 无状态（双向都要配） |
| **优先级** | 高（先匹配） | 低（兜底） |
| **典型场景** | "哪个 CVM 能访问这个 DB" | "整个子网拒绝某 IP 段" |

### 关键特性

- **白名单机制**：默认拒绝进站，出站需显式配
- **优先级**：规则按数字顺序匹配，**小数字优先级最高**
- **腾讯云白名单 = 安全组的入站规则**：客户端 IP 必须加白名单才能连数据库
- **跨账号授权**：白名单可授权其他腾讯云账号的 CVM 通过安全组引用访问

```
白名单配置示例:
  192.168.1.0/24（办公网段）   ← 直接 CIDR
  sg-12345（"运维安全组"）      ← 安全组引用
  0.0.0.0/0（所有，危险）        ← 不推荐
```

### 防火墙、iptables、netfilter 的关系（概念澄清）

**准确说：iptables 是 Linux 防火墙的"配置工具"，防火墙功能本体是内核 netfilter 框架**。

```
层次关系：
Linux 防火墙体系
├── netfilter（内核态框架，真正干活的）
│   └── 挂载点：PREROUTING/INPUT/FORWARD/OUTPUT/POSTROUTING
└── iptables（用户态工具，往 netfilter 写规则）
    └── 表：raw/mangle/nat/filter
```

- **防火墙 ≠ iptables**：防火墙是功能概念，iptables 是配置该功能的工具之一（还有更新的 nftables/firewalld）
- **"分布式"的含义**：规则不只在一台机器生效——云厂商把安全组规则**下发到每台宿主机/每块网卡的内核**执行，任何一台机器发包都过一遍本地 netfilter 规则。这就是"分布式"：**没有集中的防火墙盒子，每台机器自己拦截**
- 传统硬件防火墙是"集中式"（流量过一台专用盒子），安全组是"分布式"（每台宿主机都是防火墙）

## 北极星（Polaris）——服务发现与治理平台

> ⚠️ 注意：北极星**不是负载均衡器（LB）**，是腾讯开源的服务发现与治理平台（PolarisMesh，对标 Consul/Nacos/Eureka）。L5 是腾讯老一代"名字服务+接入"，北极星是其升级替代。

### 是什么

**客户端侧服务发现 + 治理平台**：

```
传统方式（硬编码 TGW mvip）:
  管控组件 oss/ha_scheduler/pingmgr → 配置文件写死 db_host:port（TGW mvip）
  ↓ 主备切换要改配置/依赖 TGW 切 VIP

北极星方式（服务发现）:
  管控组件（SDK/sidecar 接入）→ 北极星服务端 → 拉取"管控DB"实时地址列表
  ↓ 主备切换后北极星推送新地址，客户端自动感知
```

### 在 TDSQL-C 中的实际用途（来自知识库）

管控组件接入北极星发现**管控 DB** 地址：
- `oss / ha_scheduler / pingmgr`：`use_polaris_first = true` + `db_polaris_server_name/namespace/user`
- 替代配置 TGW mvip 的硬编码方式
- 效果：管控 DB 主备切换时，北极星下发 watch 事件，管控组件感知新地址，无需改配置

### 性能指标（知识库实测）

| 操作 | 耗时 |
|------|------|
| 初次进程启动获取服务地址 | ~400ms（增加 ha_scheduler 启动耗时 0.4s，可接受） |
| 运行中读缓存 | 平均 4µs（几乎无影响） |
| 服务端变化后客户端感知（watch 下发） | 3-6s（10s 内） |
| sidecar 本地 HTTP 获取地址 | < 50ms |

### 与 TGW/Proxy/L5 的本质区别

| 维度 | 北极星 | TGW | Proxy | L5（老） |
|------|--------|-----|-------|----------|
| **本质** | 服务发现+治理平台 | 集中式 L4 转发 | 集中式 L7 代理 | 老一代名字服务 |
| **流量路径** | **不过北极星**（客户端直连后端） | 流量过网关盒子 | 流量过 Proxy | SDK 侧调度 |
| **负载均衡位置** | 客户端 SDK 内部 | 网关侧 | 代理侧 | 客户端 SDK |
| **对标** | Consul/Nacos/Eureka | —（腾讯内部基础设施，CLB 四层底层） | RDS Proxy | — |

**关键差异**：北极星只发"地址列表"，**流量不经过它**——客户端 SDK 拿到地址后直连后端（对比 TGW：流量必须过网关盒子）。

## PrivateLink vs VPC Gateway

### 核心区别

| 维度 | PrivateLink | VPC Gateway |
|------|-------------|-------------|
| **路径** | **私网 ↔ 私网** | **公网 ↔ 私网** 或子网间 |
| **网络位置** | 双方都是 VPC/内网 | 一方公网、一方 VPC |
| **延迟** | 内网级别（< 1ms） | 公网（10-100ms）或内网 |
| **安全性** | 内网隔离，无暴露 | 需白名单/防火墙 |
| **典型场景** | 云上业务 ↔ 云数据库 | DBA 办公网 ↔ 云数据库 |

### 跨账号场景

**跨账号 = 不同腾讯云账号**，是租户隔离单位。

```
腾讯云账号 A               腾讯云账号 B
├── VPC-A                 ├── VPC-B
│     └── 云数据库实例      │     └── 业务 CVM
└── 管控不允许外部账号访问
```

跨账号访问方案：

| 方案 | 场景 | 推荐度 |
|------|------|--------|
| **PrivateLink** | A 账号数据库供 B 账号业务访问 | ⭐⭐⭐ 推荐 |
| 云联网 CCN | 双方加入同一云联网，全网互通 | ⭐⭐ 复杂组网 |
| 共享 VPC | 把 A 账号的 VPC 共享给 B | ⭐⭐ 特殊场景 |
| 公网 + 白名单 | 兜底方案 | ⭐ 不推荐 |

### 跨 VPC 互通三条路（重要）

| 方案 | 模式 | 跨账号 | 粒度 | 现状 |
|------|------|--------|------|------|
| **对等连接（Peering）** | VPC 级全网互通（像两楼间架桥，任意房间互访） | ✅ 支持（跨账号需对端账号接受） | 网络层全通 | 与云联网并存，同地域免费 |
| **云联网（CCN）** | 多 VPC 中心化互通 | 支持（双方加入同一云联网） | 网络层全通 | 复杂组网推荐 |
| **PrivateLink** | 服务级点对点（只能到指定"房间"） | ✅ 原生 | 只暴露一个服务 | **跨账号访问数据库标准方案** |

**跨账号访问数据库选 PrivateLink 而非云联网的原因**：
1. **最小权限**：只暴露数据库一个服务，消费方碰不到数据库 VPC 的其他任何资源；云联网是全网互通，权限太粗
2. **服务方可控**：数据库团队授权谁能连，业务方自助创建终端节点
3. **不占网段**：云联网要求两端网段不冲突，PrivateLink 无此要求

**对等连接详解**：两个 VPC 之间的双向私网互通通道。建立后两边路由表各加一条对端网段路由，A、B 内网直接互访。与 PrivateLink 的区别：对等连接是**网络层全互通**（整栋楼都可达），PrivateLink 是**服务层点对点**（只能到指定房间）。

### 云上 vs 线下（场景对比）

| 维度 | 云上（CVM/TKE） | 线下（办公网/IDC） |
|------|----------------|-------------------|
| **位置** | 腾讯云 VPC 内 | 公网/自建机房 |
| **有无 VPC** | 有（业务自己的 VPC） | **无**（VPC 是云上概念） |
| **访问方式** | PrivateLink（首选）/ 同 VPC 内网 | 公网 + 白名单 / VPN / 专线 |
| **延迟** | < 1ms | 10-100ms+ |

### 线下访问云数据库的完整链路（主体澄清）

线下客户端访问云数据库，链路上**两端的 NAT 主体不同**，不要混淆：

```
线下客户端 (办公网/IDC)
  │ 私网 192.168.x.x
  ↓ ①客户端侧 NAT（办公网出口路由器，不是云的）
公网传输
  ↓ ②到达数据库的公网入口
数据库 EIP/公网 VIP (139.198.x.x)  ← 云厂商提前暴露好的
  ↓ ③DNAT 进 VPC（云内部网关，对用户透明）
Proxy/TGW
  ↓ ④
数据库 RS
```

**关键澄清**：
- **"申请公网入口"的是云厂商（数据库服务方）**——数据库创建时可选开启公网地址，开的是数据库的 EIP
- **用户侧只需要能出公网**（办公网 NAT/IDC 公网出口），然后把出口 IP 加数据库白名单
- 不是"用户去申请 vpcgw"——云内部 DNAT 进 VPC 这步对用户透明
- **替代路径**：VPN/专线（不出公网，直接进 VPC，更安全低延迟）

| 线下接入方式 | 步骤 |
|-------------|------|
| **办公网 NAT 出口** | 客户端 NAT 拿公网 IP → 直连数据库公网入口（EIP） |
| **VPN 接入** | 客户端 VPN → 进 VPC 内网 → 访问数据库 |
| **专线接入** | 自建 IDC ↔ 腾讯云专线（更安全、低延迟） |

## K8s 网络：Service / ClusterIP / Overlay / Underlay

### K8s 网络的两层视角

```
┌──────────────────────────────────────┐
│ Pod A (10.244.1.5)        ← Pod 网络 │
│ Pod B (10.244.1.6)        ← Pod 网络 │
│   ↑ 互相通信靠 CNI                     │
├──────────────────────────────────────┤
│ Node 1 (10.0.1.10)        ← 节点网络 │
│ Node 2 (10.0.2.10)        ← 节点网络 │
│   ↑ 互相通信靠 VPC 路由               │
├──────────────────────────────────────┤
│ VPC 10.0.0.0/16         ← 物理网络   │
│ 路由器/NAT/TGW/Proxy                  │
└──────────────────────────────────────┘
```

Overlay vs Underlay = **CNI 选哪种方式实现 Pod 网络 ↔ Node 网络的桥接**：
- Overlay：Pod 跑在虚拟网段（10.244.x.x），Node 是 VPC 子网，CNI 用 VXLAN 封装
- Underlay：Pod 拿 Node 所在 VPC 子网的真实 IP，CNI 直接复用 VPC 网络

### Overlay/Underlay 下各层 IP 的真实状态

**Overlay 下**：
```
Node-1 (VPC Subnet: 10.0.1.0/24)
├── eth0: 10.0.1.10/24 ← 实例网卡（CVM 上是 virtio 虚拟网卡；裸金属/SR-IOV 才是物理直通），VPC 可见可路由
├── Pod-A veth pair: 10.244.1.5/24 ← 在 Pod 内是真实网卡(netns)，对 VPC 完全不可见
└── CNI bridge: cbr0/cilium_host → 把 Pod veth 和 Node eth0 桥接
```

- ✅ Node IP（10.0.1.10）= VPC IP，**真实绑网卡**
- ❌ Pod IP（10.244.1.5）= **不在 VPC 网段**，对 VPC 完全不可见
- 跨节点 Pod 通信：CNI 把 Pod 包封进 VXLAN UDP 包，外层用 Node IP 跑 VPC

**Underlay 下**（典型 TKE 集群）：
```
Node-1 绑 NIC eth0 = 10.0.1.10/24 ← Node IP
  └── Pod-A veth = 10.0.1.20/24 ← Pod IP，独立于 Node IP，是 VPC 子网里的另一个地址
Node-2 绑 NIC eth0 = 10.0.2.10/24 ← Node IP
  └── Pod-B veth = 10.0.2.20/24 ← Pod IP
```

- ✅ Node IP = VPC IP，绑 NIC
- ✅ Pod IP = **也是** VPC IP，每个 Pod 占一个独立子网 IP
- VPC 路由器同时认识 10.0.1.10（Node）和 10.0.1.20（Pod），都直接路由

| 概念 | 谁级别 | IP 性质 |
|------|--------|--------|
| **Node IP** | Node 级别 | VPC 子网 IP 之一，绑实例网卡（CVM 为虚拟网卡） |
| **Pod IP**（Underlay） | Pod 级别 | VPC 子网 IP 之一，每个 Pod 占一个真实 IP |
| **VPC 整个网段** | VPC 级别 | 包所有 Node IP 和 Pod IP |

### VPC 子网规划容量

VPC 子网规模 = 节点数 × (1 + 每节点 Pod 数)：
- 小集群：几百个 Pod → 子网 24 位掩码（254 IP）够用
- 大集群：几千 Pod → 需要更小的子网（22/21 位，提供 1000-2000 IP），或直接用 Overlay

### Service / ClusterIP / Pod IP 三层关系

```
┌─────────────────────────────────────────┐
│  K8s 集群                               │
│                                          │
│   Pod-A (10.244.1.5)  ← Pod IP         │
│   Pod-B (10.244.1.6)  ← Pod IP         │
│        ↓                                 │
│   Service "web" (10.96.0.10:80)        │
│        ↑                                 │
│   ClusterIP: 10.96.0.10 ← Service IP   │
│                                          │
└─────────────────────────────────────────┘
```

| 概念 | 作用 | 性质 |
|------|------|------|
| **Pod IP** | Pod 的网络命名空间 IP | 容器级虚拟 IP |
| **Service** | 一组 Pod 的稳定访问入口 | K8s 抽象对象 |
| **ClusterIP** | Service 的一种类型（默认） | 集群内虚拟 IP |
| **NodePort** | Service 的另一种类型 | 节点端口暴露 |
| **LoadBalancer** | 云 LB 暴露 | 公网/内网 LB |

### Service 是 K8s 抽象，ClusterIP 是其中一种类型

```
Service 类型:
  ├── ClusterIP   ← 默认，集群内虚拟 IP
  ├── NodePort    ← 每节点开端口
  ├── LoadBalancer← 云厂商 LB
  └── Headless    ← 无 ClusterIP，直接返 Pod IP
```

### ClusterIP 与 VIP 类比

| 维度 | ClusterIP | 云数据库 VIP |
|------|-----------|-------------|
| 作用域 | K8s 集群内 | VPC 内 |
| 绑定网卡 | 不绑 | 不绑 |
| 路由机制 | kube-proxy (iptables/ipvs) | VPC 路由表 / TGW |
| HA 切换 | Service 后端 Pod 重建，规则自动更新 | VIP 重绑到新 RS |

**ClusterIP 本质上就是 VIP**，只是 K8s 内的命名。

### iptables 与 ClusterIP 的关系

**kube-proxy 用 iptables 规则实现 ClusterIP 转发**：

```bash
# kube-proxy 在每台 Node 上自动生成的规则
-A KUBE-SERVICES -d 10.96.0.10/32 -p tcp --dport 80 \
    -j KUBE-SVC-XXXXX

# SVC 链随机分发给后端 Pod
-A KUBE-SVC-XXXXX -m statistic --mode random \
    --probability 0.333 -j KUBE-SEP-AAAA   # Pod-1
-A KUBE-SVC-XXXXX -m statistic --mode random \
    --probability 0.5 -j KUBE-SEP-BBBB     # Pod-2
-A KUBE-SVC-XXXXX -j KUBE-SEP-CCCC         # Pod-3
```

**ipvs 模式**：用 Linux 内核 ipvs 替代 iptables，O(1) 哈希查表，更高效。

### iptables 本身是什么（详解）

**Linux 内核 netfilter 框架的用户态配置工具**，做四件事：

| 功能 | 说明 | 谁在用 |
|------|------|--------|
| **包过滤** | 按 5 元组（src/dst IP+port+协议）允许/拒绝包 | 云安全组底层就是分布式 iptables 规则 |
| **NAT** | SNAT/DNAT 改写地址 | kube-proxy 实现 Service ClusterIP |
| **流量改写/标记** | mangle 表打 mark、限速 | QoS、策略路由 |
| **统计** | 每条规则带计数器 | 流量分析 |

**四表五链**：

```
表（优先级从高到低）: raw → mangle → nat → filter
链（包的路径）:
  入站: PREROUTING → INPUT
  转发: PREROUTING → FORWARD → POSTROUTING
  出站: OUTPUT → POSTROUTING
```

K8s 里的用法（kube-proxy 写 DNAT 规则）：

```bash
# 目的地址是 ClusterIP 的包 → DNAT 到某个 Pod IP
-A PREROUTING -d 10.96.0.10/32 -j KUBE-SVC-XXX
-A KUBE-SVC-XXX -j DNAT --to-destination 10.244.1.5:80
```

与云安全组的关系：云厂商的安全组本质上是**分布式 iptables 规则**（下发给每台 CVM/宿主机执行）。

### Overlay vs Underlay 通俗类比

一句话：**Underlay 的 Pod 是 VPC 的"一等公民"，Overlay 的 Pod 是"编外人员"**。

```
Underlay（Pod 有 VPC 身份证）:
  Node IP: 10.0.1.10（VPC 子网发的）
  Pod IP:  10.0.1.20（也是 VPC 子网发的！）
  → VPC 路由器认识 10.0.1.20，Pod 访问数据库 VIP 直接路由到达
  → 代价：Pod 数量受子网 IP 上限约束，每个 IP 要在 VPC 登记

Overlay（Pod 无 VPC 身份证，出门靠 Node 包装）:
  Node IP:  10.0.1.10（VPC 认识）
  Pod IP:   10.244.1.5（VPC 不认识这个网段！）
  → Pod 的包要出 Node 时，整个塞进 UDP 包（VXLAN 封装），
    外层写 Node 的 VPC IP，VPC 只运外层
  → 到对端 Node 拆包，还原 Pod 原始包
  → Pod 访问数据库 VIP：流量出 Node 时 SNAT 成 Node IP 才能进 VPC
```

（完整对比表与选型见 [为什么 Overlay 不直接用 VPC IP](#为什么-overlay-不直接用-vpc-ip设计动机) 一节）

### Overlay 与 VIP 关系

**Overlay 不一定 = VIP**：
- Overlay 是**网络模式**（封装方式）
- VIP 是**IP 类型**（不绑网卡）
- Overlay 下的 Pod IP 是真实但私有的（10.244.x.x）
- Overlay 也可以有 VIP（ClusterIP）

**Pod 一定运行在某个 Node 上**，Node 是物理或虚拟的机器，Node IP 是真实的。

## VXLAN 与 Pod 网络

### VXLAN 是什么

**Virtual Extensible LAN**（RFC 7348）：网络虚拟化隧道协议，给原始包套一层 UDP 头，让物理网络只看到外层 MAC/IP。

### VXLAN 头部结构

```
原始包 (Pod 网络):
  内层 MAC: Pod-A_mac → Pod-C_mac
  内层 IP:  10.244.1.5 (Pod-A) → 10.244.2.7 (Pod-C)

VXLAN 封装后 (物理网络):
  [外层 MAC][外层 IP: 10.0.1.10 → 10.0.2.10][UDP 4789][VXLAN 头(VNI, 8 字节)][内层 MAC][内层 IP][原始 payload]
```

**物理网络只看到外层**（Node IP），**Pod 网络看到内层**（Pod IP）。
VXLAN 封装总开销 ~50B（外层 MAC 14 + 外层 IP 20 + UDP 8 + VXLAN 头 8）。

### 为什么 Overlay 下 Pod 与 VPC 不能直接通

```
Overlay 模式:
  Pod-A IP: 10.244.1.5
  VPC 内数据库 VIP: 10.0.1.100

Pod-A → 10.0.1.100:
  - VPC 路由器看到目的 IP 10.0.1.100，查路由表
  - 路由表只认识 10.0.0.0/16 段，不认识 10.244.x.x
  - 结果: 路由不可达 ❌

Underlay 模式:
  Pod-A IP: 10.0.1.15（VPC 子网 IP）
  VPC 路由器看到目的 IP 10.0.1.100，查路由表
  路由表认识 10.0.1.0/24，直接转发 ✓
```

### 为什么 Overlay 不直接用 VPC IP（设计动机）

**根本原因：VPC 子网 IP 数量有限，且 Pod 数量可能远超子网容量**。

```
假设 VPC 10.0.1.0/24（254 个可用 IP）
K8s 集群有 5000 个 Pod
  ↓ 直接用 VPC IP：IP 不够 ❌
```

**Overlay 的解法**：Pod 用独立大网段（如 10.244.0.0/16，65536 个 IP），不受 VPC 限制。

**Overlay vs Underlay 完整对比（全文唯一权威表）**：

| 维度 | Underlay（Pod 用 VPC IP） | Overlay（Pod 用独立段） |
|------|---------------------------|------------------------|
| **Pod IP** | VPC 子网 IP（每个 Pod 占一个） | 独立段（如 10.244.x.x） |
| **适用规模** | 小集群（几百 Pod） | 大集群（几千到几万） |
| **VPC 子网压力** | 高（子网容量 = 节点数 × (1+每节点 Pod 数)） | 无 |
| **封装** | 无 | VXLAN 总开销 ~50B |
| **性能** | 最优 | 略低（封装开销 ~5%） |
| **配置复杂度** | 高（要算子网、规划 IP） | 低（CNI 自动分配） |
| **Pod ↔ VPC 资源（如数据库）** | **直接通**（Pod IP 即 VPC IP） | 需 Node 出口 SNAT（源 IP 改写为 Node IP） |
| **Pod 跨 Node 通信** | VPC 直接路由 | VXLAN 封装穿越 |

### Underlay/Overlay 选型决策树

```
K8s 集群规模？
├─ 小集群（≤500 Pod）
│  ├─ 性能要求极高（数据库/金融）
│  │  └─ ✅ Underlay（VPC 内直接通，无封装开销）
│  └─ 通用业务
│     └─ ✅ Underlay（简单，性能好）
│
└─ 大集群（> 500 Pod）
   ├─ 性能要求一般（Web/微服务）
   │  └─ ✅ Overlay（避开子网 IP 数量限制）
   └─ 性能要求高
      ├─ 子网够大（如 /21 位 2000 IP）
      │  └─ ⚠️ 可 Underlay（仔细规划）
      └─ 子网不够
         └─ ✅ Overlay（封装开销 ~5%，可接受）
```

| 场景 | 推荐 |
|------|------|
| TKE 标准集群（< 500 Pod） | **Underlay**（默认） |
| 大规模 TKE（数千 Pod） | **Overlay**（自动） |
| 金融/数据库/极致性能 | **Underlay**（手动规划） |
| 多 K8s 集群混合 | Overlay（隔离） |
| 跨 VPC 部署 K8s | Overlay（避免子网规划冲突） |

### "VPC 是谁申请的"

**VPC 的归属**：

| VPC 类型 | 谁申请 |
|---------|--------|
| 业务 VPC | 业务方（自己或云厂商代建） |
| 数据库 VPC | 云厂商申请，专门跑数据库 |
| 接入 VPC | 用于 PrivateLink 接入的中转 |

**数据库 VPC 通常由云厂商申请**，业务方不能直接进数据库 VPC，而是通过 PrivateLink 访问数据库 VIP。

## 复杂网络拓扑读图法

### 读图四步法

1. **找 VPC 边界**：哪些组件在哪个 VPC
2. **找网关/连接**：jnsgw/vpcgw/PrivateLink/TGW/VPN/专线
3. **找 IP 段**：私网（10/172/192）、公网、VPC 内、Pod IP
4. **找节点位置**：Pod/CVM/RS 在哪层（VPC、K8s、IDC）

### 典型复杂场景示例

```
场景: 用户 IDC 通过专线连腾讯云，访问跨账号的云数据库

用户 IDC                专线 VPC              数据库账号
───专线──→ 接入 VPC A ──对等连接──→ VPC B（数据库账号 X）
  │            │                          │
  └ CVM-1      └ 接入 CVM                 └ 云数据库 VIP 10.0.2.100
                  (DNAT 出公网/专线)
```

> 注：图为示意（对等连接支持跨账号，需对端接受）。**实际跨账号访问云数据库的标准方案是 PrivateLink**（最小权限、服务级暴露），数据库 VPC 一般不会与用户 VPC 建对等连接。

```
场景: 线下办公网 DBA 通过公网连云数据库

办公网             腾讯云公网入口          VPC 内
───公网──→  EIP (数据库入口) ──→  Proxy ──→  RW VIP
                                     │
                                     └──→  RO
```

读图要点：
- 看**每个节点的 IP/段**，判断在哪个 VPC
- 看**每条线**是私网、公网、专线、还是 VPN
- 看**箭头方向**是单向还是双向
- 看**网关/中间件**的位置（vpcgw/jnsgw/TGW/Proxy/PrivateLink）

## 关键流程链路

### Pod 访问同 VPC 内数据库（Underlay）

```
Pod-A (10.0.1.15) → 10.0.1.100（DB VIP）
  ↓
Pod-A 网络命名空间内 → Node-1 eth0 → VPC 路由器 → RS（当前主）
```

### Pod 访问同 VPC 内数据库（Overlay）

```
Pod-A (10.244.1.5) → 10.0.1.100（DB VIP）
  ↓
Pod-A netns 发包 (src 10.244.1.5, dst 10.0.1.100)
  ↓
Node-1 出口内核 SNAT/masquerade
  ↓ src 改写为 Node IP 10.0.1.10（VPC 可路由）
VPC 路由器 → 数据库 VIP → RS
  ↓ 回包到 Node IP，再按 NAT 表转回 Pod
```

**关键**：源地址被 SNAT 成 Node IP（VPC 认识的 IP），目的 VIP 不变，因此可直达；数据库看到的是 Node IP，不是 Pod IP。

**实际机制（修正）**：
- Overlay Pod 访问 VPC 内数据库 VIP：**不需要 Service 桥接**
- 真实路径：Pod 直接发起对 VIP 的连接 → 流量出 Node 时内核做 **SNAT（masquerade）**，源 IP 改写成 Node IP → Node IP 是 VPC IP，路由可达数据库 VIP → 回包回 Node 再转回 Pod
- Service（如 ExternalName）只是提供 **DNS 便利**（稳定的域名），不是网络层必需
- 例外：部分 CNI（如 TKE Global Router 或配置了 Pod CIDR 路由的环境）允许 Pod 网段路由进 VPC，则无需 SNAT

### 跨 VPC 访问（PrivateLink）

```
VPC-A 业务 CVM (10.0.1.10)
  → PrivateLink Endpoint
  → 腾讯云内网专线
  → VPC-B 数据库 VIP (10.0.2.100)
  → TGW/Proxy 转发
  → 数据库 RS
```

### 线下通过公网访问

```
本地客户端 (113.108.x.x)
  → 公网路由
  → 数据库 EIP (139.198.x.x:3306)
  → TGW/Proxy
  → 数据库 RS
```

## Misc

### 常见误解纠正

| 误解 | 正确 |
|------|------|
| "VPC 就是子网" | VPC 包含多个子网 |
| "基础网络是一个子网" | 基础网络是腾讯云全局共享的扁平网络（所有租户混在一起），不是子网 |
| "VPC 和基础网络都是一组私网 IP，可以等同" | 表象相同本质不同：基础网络=共享平面+软件隔离；VPC=独占平面+网络层隔离（overlay 虚拟出来的），安全模型完全相反（默认可达靠拒绝 vs 默认不可达靠放行） |
| "VIP 一定是公网 IP" | VIP 是私网 IP，路由层指向物理节点 |
| "VIP 绑在物理网卡上" | VIP 不绑网卡，靠路由转发 |
| "Overlay 一定是 VIP" | Overlay 是网络模式，Pod IP 是真实但私有的 |
| "Pod IP 是假的" | Pod IP 在 Pod 内是真实的（虚拟网卡） |
| "网关只工作在一层" | L4 网关核心在 L4 但也涉及 L3 路由 |
| "vpcgw 用于跨 VPC 打通" | **vpcgw 不做 VPC↔VPC 私网互通**（那是 PrivateLink/云联网/对等连接），它管 VPC 内 CDB/内网 LB/公共服务/PrivateLink 服务接入（出公网 NAT 是 natgw，专线接入是 dcgw，各司其职） |
| "VPC 内子网间需要打通" | **子网默认互通**，vpcgw 是默默转发的基础设施，用户无感 |
| "跨账号用 vpcgw" | 跨账号用 PrivateLink（最小权限、服务级暴露），vpcgw 没有跨 VPC 能力 |
| "裸金属和物理机一样" | 裸金属是云上独占物理机（接入 VPC/云管理），物理机是自己机房自己管 |
| "线下用户要申请 vpcgw" | 公网入口是云厂商（数据库服务方）提前暴露的 EIP，用户只需能出公网+加白名单 |
| "Overlay 下 Pod 访问 VPC 必须走 Service 桥接" | Service 只是 DNS 便利，网络层靠 Node 出口 SNAT（源 IP 改写为 Node IP）即可直达 VIP |
| "TGW 是腾讯云对外的 4 层 LB 产品" | TGW 是腾讯**内部**统一接入网关（基础设施，微信/QQ 等内部业务都走它）；对外产品是 CLB，四层 CLB 底层即 TGW、七层是 STGW |
| "对等连接不支持跨账号" | 支持：跨账号对等连接需对端账号接受即可建立 |
| "NAT 网关 SNAT 出口 IP 不固定" | NAT 网关必须绑 EIP：绑 1 个出口固定，绑多个才轮询不固定 |
| "iptables 和 ClusterIP 没关系" | kube-proxy 用 iptables 实现 ClusterIP 转发 |

### 高可用方案（网关层面）

| 网关类型 | 高可用方案 | 说明 |
|----------|-----------|------|
| **有状态网关**（vpcgw/jnsgw/natgw/lbnat/dcgw-nat/sxgw） | **VRRP** | 主备模式：主挂备接管，虚拟 IP 漂移 |
| **无状态网关**（pvgw/ccngw/pcgw/dcgw/xgw/mcgw） | **OSPF** | 多活模式：路由协议自动选路，等价多路径 |

### HAVIP（高可用虚拟 IP）

子网内的**自定义 IP**，用于主备场景（两个节点间做 VIP 漂移）：

```
主备模式:
  CVM-A (keepalived 主) + CVM-B (keepalived 备)
  共享一个 HAVIP（子网内未分配给任何实例的 IP）
  主挂了 → keepalived 把 HAVIP 漂移到 B
  → 需要 TCE 3.8.0+ 且打开 HAVIP 开关，宿主 vpc_mcagent 版本要求
负载模式: 用负载均衡（LB）而非 HAVIP
```

> HAVIP 是腾讯云产品化"VIP 漂移"的具体形态，与数据库 VIP 切换本质同源（都是不绑网卡、靠路由/ARP 漂移）。

### 子网广播

- 子网广播通过 **mcgw**（组播/广播网关）实现
- 默认子网关闭广播；开启后母机下发广播路由，广播流量下一跳指向 mcgw
- 子机侧需配合 `net.ipv4.icmp_echo_ignore_broadcasts = 0` 才能响应广播
