## 概述

### 一句话

**把数据库 WAL 从"写块设备"改成"写一个可复用的日志服务"**：热尾用 SSD 日志节点的 Quorum 复制做到单次网络往返（70 µs），冷数据异步批量归档到对象存储（每百万次追加 $0.00125）。相比 EBS io2 快 4 倍、便宜约 3 倍。

### 它要解决的问题

本地部署时，WAL 写本地 SSD 就完事了。云上不行——**实例本地盘是临时性的（ephemeral）**，实例故障或被释放时数据随之消失。所以日志必须落到远端持久化存储。于是有三条路，都不理想：

| 路线 | 问题 |
|------|------|
| **远端块存储**（EBS io2） | 延迟高（318 µs vs 本地 35 µs）、成本由**预配置容量 + 预配置 IOPS** 双重驱动，很贵 |
| **对象存储**（S3） | 持久性与容量成本极好，但**延迟数十毫秒 + 按次计费**，对大量小追加的 WAL 完全不现实 |
| **专有日志后端**（Socrates XLOG / TaurusDB PLog / Neon Safekeeper / AWS Journal） | 能解决问题，但**与各自引擎的复制和恢复协议紧耦合**，不可复用，且公开资料不足以还原设计 |

> **第三条路的荒诞之处**：业界早就知道通用存储服务不适合承载日志，于是每家云原生数据库都自己造了一个——**同一个问题被解决了 N 遍，但没有一个可复用的设计，学术界也缺乏对"延迟/成本/可用性"权衡的系统性理解。**

### 论文的四个贡献（作者自述）

BtrLog 是首个同时做到这四点的云日志系统：

1. 在常见的**单写者**架构下达成**单网络往返**的追加延迟；
2. 提供**可复用的服务接口**，不与特定引擎耦合；
3. 用云对象存储做**低成本、高持久性归档，且不放在关键路径上**；
4. 面向**高速数据中心网络与 NVMe SSD** 工程化，显式关注**尾延迟**与吞吐。

> 作者很诚实："新颖性不在于再造一个日志服务，而在于**把这个设计空间显式化**"。

### 核心数字速览

| 指标 | BtrLog (1 AZ) | EBS io2 | BookKeeper | 本地 SSD |
|------|--------------|---------|-----------|---------|
| 最佳中位追加延迟 | **70 µs** | 318 µs | 262 µs | ~35 µs（无可用性） |
| p99 | 79 µs @35.5K/s | 651 µs @1M/s | 无法扩展到 >240K/s | — |
| 每百万次追加成本 | **$0.00125** | $0.0036 | 更高 | — |
| 端到端（LeanStore YCSB-A） | **1×** | 0.8× | 0.5× | — |

## 理论基础

### 设计思想与权衡

#### 一、★ 单写者假设是全部性能收益的来源

这是整篇论文的支点。多写者日志系统（Corfu / Scalog / Kafka）必须有一个**排序器（sequencer）**把并发追加线性化，而这个排序 + 复制在写路径上叠加，产生可观延迟。

**而数据库 WAL 几乎天然是单写者的**：

| 架构 | 单写者的来源 |
|------|------------|
| Aurora / HyperScale / PolarDB / AlloyDB | **只有主实例产生日志**（主备架构，备库只读） |
| Spanner | 每个 Paxos 组选出 leader，所有写经 leader 定序 |
| Cosmos DB | 多区域写 API，但持久性靠"本地复制的物理分区"，顺序仍由分区内 leader 定义 |
| 并行日志（per-thread log streams） | 每条流仍是单写者，只是有多条流 |

> **这是 MySQL 也适用的观察**：MySQL 的 redo log 只有一个写者（mtr 提交时从 log buffer 写入，由 `log_writer` 线程串行刷出）。`innodb_log_writer_threads` 只是把"写"这件事挪到后台线程，**写者仍然唯一**。

**收益**：单写者 ⇒ 记录顺序由"追加序列"隐含定义 ⇒ **排序职责下沉到客户端** ⇒ 不需要独立的排序节点 ⇒ 省掉一整个网络往返。

```
多写者：  client → [sequencer] → [storage]      至少 2 RTT
单写者：  client(兼 leader) → [storage]          1 RTT
```

#### 二、延迟的下界是可计算的，工程必须逼近它

论文先用微基准标定硬件上限：

```
c6id.metal 集群（分区置放群组，无负载）
  网络往返（sockperf）        ≈ 40 µs
  SSD 写（fio）               ≈ 30 µs
  ─────────────────────────────────
  理论下界                    ≈ 70 µs
```

BtrLog 实测中位 70 µs —— **正好命中理论下界**。这个"先标定下界再实现"的方法论值得学习：它让"优化到什么程度算够"有了客观判据。

> **被否决的两个极端**：
> - **纯 DRAM 设计（RAMCloud 式）**：延迟极低，但内存成本高，且**相关失效**（数据中心断电、软件 bug）会让所有副本一起死。
> - **客户端直接用 NVMe-over-TCP 写远端 SSD**：延迟最低，但**日志所有权、写者防护（failover fencing）、远端节点故障、负载均衡**全都得客户端自己实现——复杂度爆炸。
>
> BtrLog 的选择：把这套逻辑**分布在客户端库与"感知协议"的日志节点之间**。

#### 三、对象存储放对位置就是纯收益，放错位置就是灾难

这是本文最值得记住的一条（详见[专章](#-对象存储为什么成本低延迟高)）：

| 放法 | 结果 |
|------|------|
| **放关键路径**（直接拿 S3 当 WAL 后端） | 数十毫秒延迟 + 按次计费 → 不可用 |
| **放异步归档层**（段写满后批量 PUT） | 享受低成本 + 高持久性，延迟完全无害 |

**"不在关键路径上"这五个字是全部要点。**

#### 四、Quorum 不只是容错，也是对冲延迟抖动

常规理解：Quorum（如 2/3）是为了容忍 1 个节点故障。
论文给出的第二重价值：**它是延迟的对冲机制**——不必等最慢的那个节点。

实测佐证：3 节点 Qw=2 vs 要求全部 3 个确认，半载下 Quorum 让中位延迟改善约 30 µs、p99 改善约 50 µs；**杀掉一个节点后，中位延迟从 95 µs 恶化到 115 µs（+21%）**，因为"杀掉一个节点等于关掉了一份对冲"。

### 理论溯源

| 理论 / 系统 | 本文如何继承或改造 |
|------------|------------------|
| **ARIES（Mohan et al. 1992）** | WAL 的四个操作 `append / sync / scan / read` 直接对应 ARIES 语义；**提交 LSN 必须在写路径上明确返回**——这条约束排除了 LazyLog 式"惰性排序" |
| **Quorum 复制（Gifford 1979）** | 基础容错机制；本文额外用它做延迟对冲 |
| **Viewstamped Replication / 带视图变更的领导者 Quorum** | 协议骨架与 Apache BookKeeper 同类，但针对"对象存储持久化路径"定制 |
| **Hyder（CIDR 2011）** | "共享闪存上的单一全序日志支撑 OLTP"——思想源头，启发了 Corfu 一系 |
| **FaRM / RAMCloud** | 远端 DRAM 日志做微秒级持久提交；BtrLog 用 NVMe SSD 替代 DRAM，换取抗相关失效 |

### 算法与数据结构

| 机制 | 做法 | 目的 |
|------|------|------|
| **段内前缀和** | 每个追加携带记录在段内的字节偏移（= 前序记录大小的前缀和） | 让所有节点构造出**字节级一致的段** |
| **确定性对象名 + 条件 PUT** | 一致段 → 相同哈希 → 相同对象名；`If-None-Match` 保证至多一个上传者成功 | **幂等刷盘**：3 副本只付 1 次 PUT 钱 |
| **写令牌（wtoken）兼作 epoch** | 单调递增，写入对象键与元数据 | 同时承担 fencing 与"旧世代数据过滤" |
| **提交水位线（cLSN）** | 客户端维护并随追加传播给节点，节点刷盘时写入对象元数据 | 区分"已持久化"与"已提交" |
| **LSN 窗口 W** | 客户端在 Quorum 确认 `LSN X−W` 前不发出 `LSN X` | 流水线化 + 尾随读者的保留机制 |
| **reply_to 端口字段** | 响应里带上线程自己的端口，客户端后续沿用 | 对称网络设计下的跨线程负载均衡 |

## 设计空间：为什么现有方案都不行

### 定性对比（原论文 Table 1）

| 方案 | 可用性 | 延迟 | 容量/$ | 追加/$ |
|------|-------|------|--------|--------|
| 本地 SSD | − | ++ | o | ++ |
| EBS (io2) | 1 AZ + | o | − | o |
| S3 Express | 1 AZ + | − | o | − |
| BookKeeper | 1 AZ + | o | − | o |
| **BtrLog 1 AZ** | + | **+** | **+** | **+** |
| S3 | 3 AZ **++** | **−−** | **+** | **−** |
| **BtrLog 3 AZ** | **++** | o | + | o |

> 符号：`++` 最优 / `+` 次优 / `o` 中等 / `−` 偏差 / `−−` 最差。
> **读这张表的关键**：S3 在"可用性"和"容量成本"两栏满分，在"延迟"和"按次成本"两栏垫底 —— 完美体现了对象存储的特性是**成对出现**的。

### 现有日志系统的网络跳数（原论文 Figure 1）

| 系统 | 跳数 | 关键机制 | 为什么慢 / 为什么不可用 |
|------|------|---------|----------------------|
| **Paxos / Raft / VSR** | **4 跳**（2 RTT） | 领导者合并排序 + 复制 | 领导者既是吞吐瓶颈，也是**延迟方差**来源 |
| **Corfu** | **6 跳** | 排序与存储解耦 + **链式复制** | 解耦消除了领导者瓶颈，但仍**急切排序**，且链式复制跳数多 |
| **Scalog** | **4 跳** | 排序解耦 + primary-backup | 同上，跳数减到 4，仍远高于单往返 |
| **LazyLog** | 1 RTT | **惰性排序**：先确认，LSN 读时才定 | ★ **不返回 LSN，与 ARIES 不兼容** |
| **Apache BookKeeper** | 1 RTT | 单写者，排序下放到客户端 | 可用，但**为前云时代设计**：未利用现代低延迟网络与对象存储归档 |
| **BtrLog** | **1 RTT** | 单写者 + 客户端排序 + 返回 LSN | — |

> **LazyLog 是最值得玩味的反例**：它达成了单往返，却因为"追加时不给 LSN"而无法用于数据库 WAL。ARIES 要求在写路径上就有明确定义的日志顺序与提交 LSN（commit 时要 `sync` 到某个 LSN）。**"快"不等于"可用"——接口语义的约束比延迟数字更硬。**

### 实测对比（我下载原文核对的延迟数据）

| 系统 | 延迟 | 吞吐 | 出处 |
|------|------|------|------|
| **Corfu**（NSDI'12） | 4 KB append 在 **650 µs** 内完成；跨机架镜像 append、读 <0.5 ms | 32 盘集群 append 瓶颈 ~**180K/s** | 原文 §5.1/§5.2 |
| **Scalog**（NSDI'20） | 约 **1.6 ms**（数据中心内） | 原型 **255K** 全序/s；可全序 5200 万 | 原文 §6.3 |
| **BtrLog** | **70 µs** | ~1M/s（受 SSD 1.1M IOPS 限制） | 原文 §6.1 |

Corfu/Scalog 都是"多写者 + 急切排序"，延迟 0.65~1.6 ms，比 BtrLog 高一个数量级——**量化了"单写者假设"值多少钱**。

## 核心实现一：系统架构与分层

### 四组件

```
┌─────────────────────────────────────────────────────────┐
│ (1) 客户端库（Client Library）                           │
│     嵌在 DBMS 的 WAL 子系统里，提供 append/sync/scan/read │
└──────────────┬──────────────────────────────────────────┘
               │ Quorum 写（1 RTT）
┌──────────────▼──────────────────────────────────────────┐
│ (2) 暂存层（Staging Layer）= 日志节点集群                 │
│     内存段（热尾，供回滚/日志分发快速读）                  │
│     + 本地 NVMe SSD（out-of-place 写 + fsync）           │
└──────────────┬──────────────────────────────────────────┘
               │ 段写满后异步刷（16 MB）
┌──────────────▼──────────────────────────────────────────┐
│ (3) 云对象存储（S3）                                     │
│     低成本、高持久的长期存储；冷读也走这里（聚合带宽）      │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│ (4) 元数据存储                                           │
│     日志元数据 + 集群配置；★ 直接用 S3 的条件写实现，      │
│     不需要 ZooKeeper / etcd                              │
└─────────────────────────────────────────────────────────┘
```

**为什么元数据可以复用 S3**：BtrLog 的元数据操作**很少**（只在 open / failover 时发生），而 S3 提供 `If-Match` / `If-None-Match` 的**条件写（CAS）语义**，正好够用。省掉一整个协调系统的部署与运维。

### 对外接口

单写者、只追加的日志抽象，四个 WAL 兼容操作：

| 操作 | ARIES 对应 | 语义 |
|------|-----------|------|
| `append` | 追加日志记录 | 返回成功（已 Quorum 持久化） |
| `sync` | **forcing the log** | 确保到某 LSN 为止全部持久化 |
| `scan` | 重启恢复 | 从给定 LSN 开始读 |
| `read` | undo 处理 | 按 LSN 取单条记录 |

故障转移、元数据更新等控制操作在客户端 **open** 日志时透明完成。

> **与文件接口的关键差别**：论文特别指出，文件系统式日志需要自己防 torn write、自己判断"最后一条成功写入的记录在哪"。而 BtrLog 因为**记录级原子性 + failover 支持**，这两个问题天然不存在。

## 核心实现二：写路径（单往返提交）

### 流程

```
客户端                          日志节点 L1/L2/L3
   │                                  │
   │ ① open（带 wtoken）─────────────▶│ 安装令牌，等 Quorum 确认
   │                                  │
   │ ② append(nLSN, cLSN, offset, payload)  ──并行发给所有节点──▶
   │                                  │ ③ 写入内存段
   │                                  │ ④ out-of-place 写本地 NVMe SSD + fsync
   │◀──────── ack（Quorum 个）────────│ ⑤ 只有 fsync 完成才 ack
   │                                  │
   │ ⑥ 收齐 Quorum → 返回 DBMS 成功    │ ⑦ 段满 → 异步 PUT 到 S3
```

**追加请求携带三个字段**（除 payload 外）：

| 字段 | 含义 | 作用 |
|------|------|------|
| `nLSN` | 本记录的 LSN | 客户端本地计数器分配 |
| `cLSN` | **最后已提交 LSN**（提交水位线） | 供读者区分已提交/未提交 |
| `offset` | 记录在**当前段内的字节偏移** | **由前序记录大小的前缀和算出** |

**关键约束**：
- 节点**必须等 SSD 写 + fsync 完成才 ack**（不能只写内存）。
- 客户端**按 LSN 顺序确认**（多条在途时），以维持 ARIES 语义。
- 排序由客户端驱动 ⇒ 消除独立排序器 ⇒ 单往返。

### 幂等段刷盘（省钱的巧思）

问题：3 个节点都刷同一个段，要付 3 倍 PUT 钱。

解法链条：

```
① 前缀和 ⇒ 所有节点构造出字节级一致的段
        ↓
② 一致段 ⇒ 相同的加密哈希 ⇒ 相同的确定性对象名
        ↓
③ 节点用条件 PUT（S3 If-None-Match）创建 ⇒ 并发上传者至多一个成功
        ↓
④ 进一步：PUT 前先查对象是否已存在，存在则跳过
```

结果：**3 副本只付 1 次 PUT 钱**。

另外两个细节：
- 因为刷盘**不在关键路径上**，可以用**开销较高的加密哈希**（杜绝意外碰撞），不必为了省 CPU 用弱哈希。
- 丢包或写者防护导致各节点哈希不同时，**容忍重复刷盘**，把去重推迟到读操作（减少协调开销）。

## 核心实现三：读路径与冷热分层

| 类型 | 数据在哪 | 用途 |
|------|---------|------|
| **热读** | 日志节点的**内存段** | 事务回滚、日志分发（log shipping）、只读副本 |
| **冷读** | 对象存储的已刷盘段 | 时点恢复、崩溃后重放（利用 S3 的聚合读带宽） |

客户端根据请求的 LSN 区间与复制过来的提交水位线**透明路由**。

**热读的两个优化**：

1. **乐观单节点读**：先只读一个节点，遇到缺口或发现该节点 cLSN 过时，再退化成 Quorum 读。
2. **延迟驱逐（deferred eviction）**：靠 **LSN 窗口**机制保证"最近可能要被读的记录还没被刷到 S3"。

**冷读的索引**：对象键里编码 `log ID + epoch + LSN range + 数据哈希`，客户端可以用 `LIST` 建索引，并靠节点提供的元数据（如 last flushed LSN）增量维护。

## 核心实现四：部署形态（单 AZ / 多 AZ / AZ+1）

### 单 AZ

- 日志节点与客户端同 AZ：**AZ 内 RTT ≈ 100 µs，且流量免费**。
- 节点放在**分区置放群组**（partitioned placement groups）里，降低机架级电源/网络故障的相关性。
- **整个 AZ 挂掉时**：BtrLog 不可用，但**数据仍然持久**（因为记录已写实例本地 SSD，断电重启后仍在）；已刷到 S3 的记录因为跨 AZ 复制，在宕机期间仍可读。

> 这体现了"持久性"与"可用性"的分离：单 AZ 部署**保证持久、不保证 AZ 级可用**。

### 多 AZ 与 AZ+1

朴素做法：3 节点分到 3 个 AZ。**不够！** 因为：

```
AZ 整体故障（损失 1 个节点）+ 另一个 AZ 里一块 SSD 坏（再损失 1 个）
  ⇒ 只剩 1/3 < 2/3 仲裁 ⇒ 不可读
```

BtrLog 的解法：**6 节点，每个 AZ 2 个**。

| 故障 | 结果 |
|------|------|
| 损失任意 2 个节点 或 整个 AZ | **仍可写**（4/6 追加仲裁） |
| 损失至多 3 个节点 | **仍可读**（3/6 读仲裁） |

即便 6 节点，仍把记录持久化到本地 SSD，以防**相关软件故障**（软件 bug 会让所有节点同时死，副本数再多也没用——这是作者反复强调的点）。

### 分层复制：把跨 AZ 流量费砍一半

问题：跨 AZ 流量要钱。1 亿条 1 KB 记录从 AZ1 复制到 AZ2 = 传输 100 GB = **$2**。若客户端把每条追加发给全部 4 个远端副本 → **4 × $2 = $8**。

解法：**客户端只发给每个 AZ 中的一个节点，由它在 AZ 内转发给同 AZ 的伙伴**。

```
朴素：  client ──▶ AZ2-N1, AZ2-N2, AZ3-N1, AZ3-N2     （4 份跨 AZ 流量）
分层：  client ──▶ AZ2-N1 ──(AZ内)──▶ AZ2-N2           （2 份跨 AZ 流量）
        client ──▶ AZ3-N1 ──(AZ内)──▶ AZ3-N2
```

**成本减半，延迟只轻微增加**——因为 AZ 内延迟（~100 µs）远低于跨 AZ 延迟（~500 µs）。

## 核心实现五：容错协议

### 故障模型与形式化

- **非拜占庭崩溃停止（crash-stop）**，异步网络。容忍：消息丢失、乱序、重复、延迟、网络分区、日志节点故障、客户端故障。
- **对象存储与元数据存储被视为可靠组件**（S3 宣称 99.99% 可用性、11 个 9 持久性）。
- 两条不变量：**(i) 记录按序提交；(ii) 故障模型内已提交条目不丢失**。
- **已用 TLA+ 形式化并通过 model checking**，工件开源。

### 4.1 无故障快速路径

```
① 客户端在元数据存储初始化日志元数据（如段大小 bSize）
② 从元数据存储取写令牌 wtoken
③ open 请求把 wtoken 安装到所有日志节点，等待 Quorum 确认
④ 此后每次 append 携带 (nLSN, cLSN, offset, payload)
⑤ 段满 → 异步条件 PUT 到 S3
```

### 4.2 客户端故障转移（最精妙的部分）

因为客户端承担领导者角色，客户端故障需要显式的转移协议。核心挑战：**维持单写者不变量、防止脑裂**。

**运行示例**（原论文 Figure 4）：客户端 C1 被网络分区隔离，只能连到 L1；新客户端 C2 要以写者身份接管。

**第一步：写者防护（fencing）**

```
C2 原语性地把日志的 wtoken 从 1 递增到 2（原子元数据操作）
  → open 请求把新令牌装到日志节点，等写入 Quorum 确认
  → 节点只接受它见过的最高令牌；见过更高的就拒绝并返回该值
  → 拿不到 Quorum 确认 → 放弃接管，向应用报告失败
```

**第二步：找日志尾（★ 刻意不读对象存储）**

> 论文这里点出了一个微妙之处：C2 连不上 L1，但仍**可能看到 L1 已刷入 S3 的段**。**朴素地查 S3 会给 failover 加上数十毫秒延迟**，所以协议**刻意不把对象存储读放在关键路径上**。

做法：新写者找出"读 Quorum 所支持的最大连续可恢复 LSN 前缀"。为加速，**节点在确认 wtoken 安装时捎带自己的最后已提交水位线**，客户端从观察到的最高水位（示例中 cLSN=2）开始顺序读。

**第三步：判定哪些数据已提交（保守推断）**

这是全文最精妙的一处推理。难点在于：

- Quorum 复制**会因消息丢失产生缺口**；
- 多条追加在途时，**最后已提交水位线可能滞后**。

反例：C2 只看到 LSN 3 的**一份副本**，但此前 C1 已把它复制到 2/3 节点**并向应用报告成功**（C1 的 cLSN=3）。

> 如果严格要求"写者必须看到 Quorum 份副本"才算已提交 —— **反而会造成数据丢失**。

所以规则是**保守的**：

```
凡 Quorum 节点中至少一个存在的连续 LSN ⇒ 纳入日志尾（视为可能已提交）
只有读 Quorum 确认缺席的 LSN ⇒ 才推断为未提交
```

示例中 LSN 4 虽然**已经持久化在 S3 里**，但读 Quorum 确认它缺席 ⇒ C2 推断它未提交。

> **这条不变量值得单独记住**：**对象存储里的数据只是"已持久化（durable）"，不一定是"已提交（committed）"。**

**第四步：修复与续写**

欠复制的记录（示例中的 LSN 2、3）在网络分区下更容易丢（LSN 2 唯一可访问的副本会随 L3 故障而丢）。新客户端用新 wtoken 把它们**重新复制到所有节点**。若新客户端在此期间也被防护 → 转移中止，通知应用重试；协议保证并发修复最终恢复出**相同或更高的**日志尾。

转移还顺带重建了新写者的全部状态：最后已提交 LSN、下一个 LSN（nLSN）、**以及各记录的字节偏移**（用于重建段前缀和，继续幂等刷盘）。

### 4.3 节点故障

**检测**：**不靠客户端**（客户端空闲或崩溃时就没人发现了），而是**日志节点之间点对点心跳**。

**处理**：传统协议（VSR/Raft/Corfu/Scalog）是存活节点向恢复节点**重复制数据**，健康节点还要额外服务恢复流量。BtrLog 改成：

```
把日志段快照刷进对象存储（覆盖故障检测时刻之前的全部 LSN）
```

好处：① 减轻健康节点负载；② 新加入/恢复中的节点**拿到当前 wtoken 后立即能接受新写入**。

**两个省钱优化**：
1. 只在检测到 **`N − Qw` 个节点故障**时才触发刷盘（3 节点 Qw=2 时一个故障就触发；6 节点 Qw=4 时要两个）。
2. **确定性地为每条日志指定一个刷新领导者**：领导者立即刷，其他节点先查对象是否已存在再决定。

**节点替换目前靠人工**（移除故障节点，用相同 DNS 名或 IP 接入新节点）——论文明确列为未来工作。

### 4.4 不可靠网络：把麻烦推迟到读路径

**设计取舍：写路径保持精简，网络引发的麻烦全部推迟到读路径处理。**

| 问题 | 处理 |
|------|------|
| **未提交数据进了 S3**（如 failover 进行中节点刷了盘） | 靠 **cLSN 水位线**过滤：节点刷盘时把 cLSN 写进对象元数据；从 S3 读时据此过滤 |
| **段之间有缺口与重叠**（Quorum 复制导致：部分节点有 LSN 1/3，另一些有 2/4） | 客户端从 S3 读时**透明合并** |
| **重复数据**：旧写者的在途请求填满段触发刷盘，新写者又以相同 LSN 追加新数据 → 同一 LSN 多份副本 | **wtoken 兼作 epoch**：每个刷盘对象在键与元数据里编码世代，读时忽略旧世代 |

## 核心实现六：面向微秒级的工程实现

### 延迟下界的实现目标

```
网络往返 40 µs + SSD 写 30 µs = 70 µs 目标
⇒ 一次系统调用、一次大额分配就可能让延迟恶化几个百分点
⇒ 必须精细控制缓存未命中、内存分配、系统调用
```

### 技术栈

| 选择 | 理由 |
|------|------|
| **Rust** | 性能与内存安全 |
| **自研 io_uring 异步运行时** | "没找到兼具稳定低延迟与可观测性的现成 Rust 异步运行时"；io_uring 可以把 `send`/`recv`/`write` **批量化提交系统调用** |
| **UDP（默认）** | ★ **Quorum 协议本身就替代了 TCP 的多数保证**（可靠性由协议层做），因此不必付 TCP 的流与连接管理开销 |

> **"用 UDP 是因为上层协议已经做了可靠性"** —— 这是个漂亮的跨层取舍：既然 Quorum + 重试已经处理了丢包，TCP 的重传与拥塞控制就是重复劳动，还带来延迟抖动。

### 多核架构

**核心观察**：每条日志内部要求顺序语义，而最常见的 `append` 只需极少 CPU 周期 ⇒ **每条日志由一个线程独占、顺序处理**。

```
线程收到消息
  ① 校验 + 拷进内存日志段（apply）
  ② 异步写本地 SSD，保证 fsync 语义（write）
  ③ 数据持久后应答客户端（reply）
  ④ 按需异步把写满的段刷到 S3
```

**每核一个线程 + 协作式调度**：不用"同步 I/O + 让 OS 调度其他线程"，因为线程超额订阅与 OS 调度会带来**延迟尖刺**。改为每核一线程，在线程内交错 I/O 与 CPU 工作。

**对称网络设计**：**不为网络单设专用线程**（那要求每个包跨线程同步，在 CPU 少的小节点上还要浪费一个核）。每个线程在**自己的端口**上用 io_uring 收包并直接处理。

**对称设计的代价与补救**：客户端直发线程时，日志段无法在线程间均衡；而多租户负载里高频与低频租户并存，均衡不可省。解法是协议里的 **`reply_to` 端口字段**：

```
节点可以把消息内部转发给其他线程并移交连接
  → 接收线程用自己的端口直接应答客户端，并在 reply_to 里带上自己的端口
  → 客户端此后沿用该端口，直到日志再迁移到别的线程
```

**S3 集成放在专用线程**：AWS Rust S3 SDK 存在**单数毫秒级的阻塞操作**，放在常规工作线程上会拖垮延迟。

**并发追加的 LSN 窗口 W**：

```
客户端在 Quorum 确认 LSN X−W 之前不会发出 LSN X
日志节点延迟刷新与窗口重叠的段（保证记录仍在内存可读）
```

双重作用：① 流水线化；② **尾随读者（如数据库备机）的保留机制**——窗口越大越能容纳慢读者，但每条活跃日志占的内存也越多。

## 评估：全量数据

### 实验环境

- 3 台带本地 SSD 的 **c6id.metal**（日志节点）+ 1 台 **c6in.metal**（客户端），AWS eu-central-1，分区置放群组，Linux 6.14。
- 对比系统：Apache BookKeeper（默认配置 + SSD 优化配置）、EBS io2（直接挂给客户端当裸块设备，不套文件系统，与 BtrLog 写本地 SSD 对齐）。
- 追加大小 **128 B**（依据 YCSB / TPC-C / pgbench 观测到的日志记录写入大小），开环基准，泊松调度，关闭写批量化。
- 成本对比用 **1 KiB 追加**、4 条合并成 1 个 4 KiB I/O（吞吐优先）。

> BookKeeper 默认配置会把追加**缓冲最长 2 ms 再组刷盘**——这个数字只有传统 HDD 延迟的零头，却已是**现代 SSD 写延迟的 60 倍**。SSD 优化配置彻底去掉缓冲、按 4 KiB 对齐、禁用页缓存、RAID0 + XFS。

### 6.1 延迟（Figure 6）

| 系统 | 最佳中位延迟 | 满载表现 |
|------|------------|---------|
| BookKeeper（默认） | **从未低于 2 ms**（图中不可见） | 无法扩展到 >240K/s |
| BookKeeper（SSD 优化） | 262 µs @6.8K/s | 负载一高迅速恶化 |
| EBS io2 | **318 µs** | 接近 1M/s 时中位 503 µs、p99 651 µs；**预配置 IOPS 饱和后延迟超出图示范围** |
| **BtrLog** | **70 µs（p99 79 µs）@35.5K/s** | 半载（~500K/s）中位 111 µs；满载（1M/s）中位 **188 µs** |

**过载行为**：BtrLog **限制内部队列长度、饱和后丢弃超额请求**，从而支撑过载检测与准入延迟上界——所以**没有**出现接近满载时延迟急剧上扬的曲线。

**峰值容量**：服务 2186 条并发活跃日志，日志节点占 71 GiB 内存，**平均每条日志 32 MiB**。

> **两个容量约束**：最大追加速率受 **SSD IOPS** 限制；可存日志数受**内存**限制。生产实现应把低频日志的段刷到 SSD 或 S3。

**可选优化**：对持久性要求较低的应用可以**关闭 SSD 写**（只保留内存段 + S3 刷盘），中位延迟再降约 50%——因为单 AZ 内 SSD 写延迟（35 µs）与网络往返（40 µs）几乎相当。

### 6.2 节点故障与 Quorum 大小（Figure 7/8）

| 实验 | 结果 |
|------|------|
| 恒定 400K/s 负载下杀掉一个随机日志节点 | 持续成功；中位 95 → **115 µs**（+21%），p99 192 → **221 µs**（+15%） |
| Qw=2 vs Qw=3（3 节点，半载 500K/s） | Quorum 使中位改善 **~30 µs**、p99 改善 **~50 µs** |

### 6.3 跨 AZ

客户端到三个日志节点的空闲中位网络延迟分别为 **270 / 440 / 540 µs**（sockperf，随区域而异）⇒ **追加延迟由跨 AZ 网络延迟主导**。

> 结合单 AZ 结果：**单 AZ BtrLog 比 EBS io2 快 4 倍**；**三节点跨 AZ 的 BtrLog 在同等吞吐下比单 AZ 的预配置 EBS 卷慢 12%**——但换来多 AZ 可用性与 WAL 优化的接口。

### 6.4 端到端（LeanStore + YCSB-A）

LeanStore 的自主提交协议为**每个工作线程维护一条独立刷盘的日志流**，恰好契合 BtrLog 的多日志流接口。

| WAL 后端 | 相对吞吐 |
|----------|---------|
| **BtrLog** | **1×** |
| EBS io2 | 0.8×（即 BtrLog 是它的 **1.25×**） |
| EBS gp3 | 0.33×（即 **3×**） |
| BookKeeper | 0.5×（即 **2×**） |

> 结论：**原先依赖 EBS io2 存 WAL 的系统，可以换成一个无需预配置的多租户服务，同时在简单的只追加接口上获得更高的事务吞吐。**

**归一化方法**：统一折算为 **per-append 成本**。

| 系统 | 计算依据 | 每百万次追加成本 |
|------|---------|----------------|
| **EBS io2** | 256,000 IOPS = **$9,651.20/月**，30 天月 ⇒ $1.45×10⁻⁸/IO ⇒ $0.0145/百万 I/O | **$0.0036** |
| EBS gp3 | 80,000 IOPS | （图中另一点） |

**结果**：BtrLog 在单 AZ 与多 AZ 两个可用性等级中都取得**最优的成本/延迟权衡**。

### 排除了"AWS 特例"的测量（最有说服力的一组）

公有块存储服务 vs 「网络 + 本地 SSD」基线：

| 云 | 网络+本地 SSD 基线 | 公有块存储服务 | 倍数 |
|----|-----------------|--------------|------|
| **AWS** | 76 µs | 311 µs | **4.1×** |
| **GCP** | 71 µs | 453 µs | **6.4×** |
| **Azure** | 301 µs | 776 µs | **2.6×** |

**⇒ 各家超大规模云的块存储服务普遍没有为低延迟 WAL 追加做优化。**

架构解释（论文原话）：
1. **EBS 的持久性由链式复制（chain replication）保证**，追加路径的网络跳数多于客户端驱动的 Quorum 复制；
2. **更宏观地看**：远端块存储暴露的是**通用块设备抽象**而非只追加接口，天然无法为小尺寸 WAL 追加做激进优化。

> 与 BookKeeper 的差距则归因于**实现选择**：两者用同样的客户端驱动 Quorum 复制，Java 的网络与 SSD I/O 原语也能达到与 Rust/C 相当的延迟，但 BookKeeper **围绕毫秒级 HDD 时代设计**，未适配现代低延迟网络与 NVMe SSD。

## ★ 对象存储：为什么成本低、延迟高

> 这一节是把论文里的论据系统化。它回答的是"为什么 S3 在 Table 1 里同时拿到两个 ++ 和两个 −−"。

### 核心论断：这是同一个设计选择的两面

对象存储把**"低延迟"这项 SLA 从契约里拿掉了**，换来了后面所有的成本优势。**你没法只买其中一半。**

### 成本低：六个结构性原因

| # | 原因 | 机制 |
|---|------|------|
| 1 | **★ EC 纠删码而非三副本** | 对象**不可变** ⇒ 一旦写好不再修改 ⇒ 天然适合 EC（如 6+3，冗余 1.5×）；块存储要支持原地改写，副本必须完整可写，只能整份复制（3×）。**光这一条就省掉一半以上存储成本** |
| 2 | **介质可以为 $/TB 优化** | 目标是每 TB 成本与聚合带宽，可以用大容量 QLC/HDD + 高密度 JBOD；块存储要为随机写延迟买单，必须用 NVMe SSD + 高性能网络 |
| 3 | **★ 无预配置成本** | 块存储按"**预配置容量 + 预配置 IOPS**"收费（io2 256K IOPS = **$9,651/月**，闲置也付钱）；对象存储按实际用量，**闲置成本严格为零** |
| 4 | **多租户池化** | 全球规模共享，一个租户的白天是另一个租户的夜里，削峰填谷后平均利用率极高 |
| 5 | **语义简单降低实现/运维成本** | 只有 PUT/GET/DELETE、不可变、无块级一致性 SLA ⇒ 元数据可大规模分片、可最终一致、数据修复/搬迁/再平衡几乎全自动 |
| 6 | **生命周期自动化** | 不可变对象天然适合自动降级（标准 → 低频 → 归档 → 深度归档），冷数据成本再降一个数量级 |

### 延迟高：七个原因，从接口往下拆

论文原话：**"object storage writes take tens of milliseconds"**（引用 [18]：Bodner et al., EDBT 2025，serverless 基础设施实测）。

| # | 原因 | 说明 |
|---|------|------|
| 1 | **接口是 HTTP/REST，不是块协议** | 一次 PUT 要走 DNS → LB → TLS → HTTP；块存储是 NVMe-oF / 自研协议，直接打底层 |
| 2 | **★ 写入路径跨 AZ、跨多设施** | 11 个 9 持久性 = 跨多 AZ + EC；一次 PUT 要等多设施确认。跨 AZ RTT 起步 500 µs，多跳 + 排队 + 扇出 ⇒ **毫秒是必然的** |
| 3 | **★ 不可变语义：不支持追加** | 最小操作单位是**整个对象**。WAL 是几百字节的小追加流，只能用 multipart upload（还得 finalize）或重写整个对象。**不是"慢一点"，是语义根本不匹配** |
| 4 | **全局命名空间与索引服务** | 每次 PUT 要先访问/更新元数据层 = 额外网络跳数；块存储的 LBA→物理块映射是本地紧耦合的 |
| 5 | **SDK 本身有毫秒级阻塞** | 论文实测 AWS Rust S3 SDK 有**单数毫秒级**阻塞操作，必须放专用线程 |
| 6 | **设计目标就不是延迟** | 优化的是聚合带宽（GB/s 扫描）与 $/TB；数据结构（大分片、EC 条带、HDD 友好）天然不适合小 I/O |
| 7 | **★ 按次计费反作用于延迟** | 为摊薄 PUT 费用（S3 Standard $0.005/1000 PUT），所有系统都被迫**攒批**（BtrLog 攒到 16 MB）⇒ **经济模型把延迟"攒"成了毫秒级** |

### 量级对照

```
本地 NVMe SSD 写      35 µs      ┃
同 AZ 网络 RTT        40~100 µs  ┃ 微秒级
EBS io2 写（最佳）    318 µs     ┃
跨 AZ 网络 RTT        ~500 µs    ┛
─────────────────────────────────────────────
S3 PUT                数十 ms    ┃ 毫秒级（差 3 个数量级）
```

### 论文的应对：分层，而不是二选一

```
热尾（最近未刷盘的记录） → SSD 日志节点 Quorum 复制   70 µs，承担低延迟
冷数据（写满 16 MB 的段）→ 异步归档到 S3            数十 ms，但没人等它
```

原文：*"exploiting S3's low storage cost without suffering from its high latency"*。

**这条思路的普适性**：Kafka 的分层存储、Pulsar/Pravega 向对象存储卸载、Aurora/Socrates/OceanBase/Neon 集成对象存储降成本——**所有系统都用了同一个模式**：对象存储做归档层，绝不放关键路径。

## 对 MySQL 与云数据库的启示

> 这一节是知识库视角的延伸，不是论文内容。

### 一、MySQL 现在的 WAL 是怎么写的

MySQL 8.0.39 的 redo 路径（详见 [`../innodb/io.md`](../innodb/io.md)）：

```
用户线程 mtr_commit → 拷贝进 log buffer（log0buf.cc）
log_writer 线程     → log_write_buffer → Log_file_handle::write → pwrite（同步）
log_flusher 线程    → log_flush_low → Log_file_handle::fsync → fsync/fdatasync
```

- **写者唯一**（`log_writer` 单线程刷出），与 BtrLog 的"单写者"假设吻合；
- 但**接口是文件/块设备语义**（`pwrite` + `fsync`），不是 `append`/`sync` 语义；
- `innodb_flush_log_at_trx_commit=1` 时每次提交都要等 fsync ⇒ **提交延迟 = EBS 的 fsync 延迟（318 µs 量级）**。

### 二、如果换成 BtrLog 式接口会怎样

| 现在（块设备） | 换成日志服务后 |
|--------------|--------------|
| `pwrite` 到 redo 文件 | `append(record)` 到日志服务 |
| `fsync` | `sync(lsn)` |
| 靠 `FIL_PAGE_LSN` 与文件偏移定位 | 靠 **LSN** 定位（服务分配偏移） |
| 崩溃恢复时扫描 redo 文件找最后一条有效记录 | **记录级原子性**，不需要防 torn write，不需要找"最后成功记录" |
| redo 文件空间需要预分配与循环复用 | 段写满即归档，空间由服务管理 |

**语义映射**：`innodb_flush_log_at_trx_commit` 的三档在日志服务上变得更清晰——

| 值 | 块设备语义 | 日志服务语义 |
|----|-----------|------------|
| 1 | 每次提交 fsync | 每次提交 `sync`（等 Quorum 持久化） |
| 2 | 只 `pwrite`，不 fsync | 只 `append`（已 Quorum 持久化但未…——**这里是语义错配处**） |
| 0 | 完全后台 | 完全后台 |

> **关键差异**：BtrLog 的 `append` 返回就意味着**已经 Quorum 持久化到 SSD**（不像 `pwrite` 只到 page cache）。所以 `=2` 这一档在日志服务上失去了原本的意义——**"写到 OS 但不 fsync"这个中间态不存在了**。这恰恰说明：换接口不只是换实现，语义要重新设计。

### 三、与云数据库的现实对照

| 系统 | 日志怎么落 | 属于哪一类 |
|------|-----------|-----------|
| **RDS（AWS/阿里/腾讯）** | redo 写在云盘（EBS/ESSD）上 | **论文批评的那一类**：简单但慢且贵 |
| **Aurora** | redo 直接发给存储层，存储层自己回放 | "日志即数据库"，存储理解 redo |
| **PolarDB / TDSQL-C** | 类似，共享存储 + redo 物理复制 | 同上 |
| **BtrLog 设想** | 独立的、可复用的日志服务 | 把 Aurora 那一套**从存储层剥离成公共服务** |

> **BtrLog 的意义**：Aurora 证明了"把日志交给理解它的存储层"是对的，但那个存储层是每家私有的。BtrLog 想做的是**把这一层变成可复用的基础设施**——就像 Aurora DSQL / S3 / DynamoDB / Lambda / Kinesis 共用 AWS 内部的 Journal 服务那样。

### 四、★ 正式对照：BtrLog 的四条设计标准 vs 现状差距

论文自述的四个贡献，正好可以作为**评估任何 WAL 后端**的四条标准。逐条对照现状：

| BtrLog 标准 | MySQL 8.0.39 现状 | 差距 |
|---|---|---|
| **① 单写者 ⇒ 单网络往返提交** | MySQL **满足单写者**（redo 由 `log_writer` 单一线程串行刷出），但**没有独立的排序/复制服务**——复制由本地 redo 文件 + 磁盘承载 | 中。要把"LSN 分配 + Quorum 复制"从磁盘语义升级为服务语义 |
| **② 可复用的服务接口**（不与引擎耦合） | **完全没有**。redo 与 InnoDB 存储层紧耦合：页格式、`FIL_PAGE_LSN`、checkpoint、dblwr 全绑在一起 | **大**。这是 Aurora / Socrates / TaurusDB / Neon 各自造一套的根本原因 |
| **③ 对象存储归档，且不在关键路径** | **没有归档层**。redo 文件循环复用（`innodb_redo_log_capacity`），冷日志直接被覆盖 | 中。需要"段化 + 写满即异步 PUT" |
| **④ 面向微秒级网络 / NVMe 的工程化** | 差距最大：**无 io_uring**（仍是 libaio）、**用 TCP 而非 UDP**、无对称网络设计、AIO 槽位默认仅几十个 | **大**。论文的 70 µs 里，协议只占一半，另一半是工程 |

### 接口语义对照（★ 换接口等于换语义，不只是换实现）

| BtrLog 接口 | MySQL 现在的等价物 | 语义差异 |
|---|---|---|
| `append(record)` | `log_buffer_write` + `pwrite` 到 redo 文件 | ★ BtrLog 的 `append` 返回即**已 Quorum 持久化到 SSD**；MySQL 的 `pwrite` 只到 OS（甚至只到 log buffer） |
| `sync(lsn)` | `log_flush_low` → `fsync` | 语义接近，但 MySQL 的 "提交 LSN" 是本地文件偏移 |
| `scan(lsn)` | 崩溃恢复时扫描 redo 文件 | BtrLog 从对象存储流式读；MySQL 从本地文件随机读 |
| `read(lsn)` | undo 处理时按 LSN 取记录 | BtrLog 是**记录级**寻址；MySQL 是**文件偏移**寻址 |
| `open()`（含 fencing） | 无（靠 `LOG_FILE_HDR` 与 checkpoint） | ★ BtrLog 的 failover 有 wtoken 防护；MySQL 靠单机文件锁 |

#### ★ 最反直觉的一处：`innodb_flush_log_at_trx_commit=2` 会失去意义

现在三档的语义是：

| 值 | 含义 |
|---|---|
| `1` | 每次提交 fsync redo |
| `2` | 只 `pwrite` 不 fsync（**OS 崩溃会丢数据**） |
| `0` | 完全后台（丢约 1s） |

换成 BtrLog 式接口后：`append` 返回就意味着**已经 Quorum 持久化到远端 SSD**，根本不存在"写到 OS 但没 fsync"这个中间态。于是 `=2` 这一档**在语义上消失了**——要么 `=1`（等 Quorum），要么退化成"客户端攒批"（那是 BtrLog 的 LSN 窗口，不是 MySQL 的 flush 语义）。

> 这个例子说明：**日志层的抽象换了，上层的持久性旋钮也要重新设计**，不是简单映射。

### 改造 MySQL 需要动的地方（如果做）

| 模块 | 现状 | 需要改成 |
|---|---|---|
| redo 写入 | `log_writer` 线程 `pwrite` 本地文件 | 客户端库 `append` 到日志服务 |
| LSN 分配 | 服务端（log_t 内部） | **客户端分配**（单写者 ⇒ 可以） |
| 提交等待 | 等 `flushed_to_disk_lsn` | 等 Quorum ack（单 RTT） |
| 崩溃恢复 | 扫描本地 redo 文件 | 从对象存储 `scan` + 合并重叠段 |
| dblwr | 防半页写（本地盘语义） | 若日志服务保证记录原子性，dblwr 可简化（但页写仍需防 torn page） |
| 归档 | 无 | 段写满异步 PUT S3 |

> 现实里没有人在社区版 MySQL 上做这个——都是各家在自己的云原生引擎里做（Aurora / PolarDB / TDSQL-C），因为它们同时控制存储层。

### 五、对自建/自建 RDS 的实用建议

即使不用 BtrLog，论文的测量也给出了可操作的结论：

1. **别把 redo 放在通用云盘上还指望低延迟**——三朵云都是 2.6~6.4× 的差距，这是架构性的，不是配置问题。
2. **如果必须放云盘**：`io2` 的 318 µs 已经是最好的通用选项；`gp3` 更便宜但更慢。
3. **降低 fsync 频率的收益是直接的**：`innodb_flush_log_at_trx_commit=2` 让 fsync 变成每秒一次（代价是 OS 崩溃丢数据）——这正是"用持久性换延迟"的经典权衡。
4. **关注 p99 而不只是中位数**：EBS 满载时 p99 651 µs vs 中位 503 µs，尾部才是事务抖动的来源。

## 批判性审视：论文的边界与开放问题

### 论文自己列出的

| 项 | 说明 |
|----|------|
| **只实现了无故障快速路径** | 故障路径只做了 TLA+ 建模，**原型未实现** |
| **多租户形态缺认证网关** | 需要 HTTP/gRPC 网关（额外约 40 µs，但仍显著快于 EBS/BookKeeper） |
| **节点替换靠人工** | 自动化替换与集群重配置是未来工作 |
| **成本估算偏乐观** | "对所有系统都采用满负荷最佳情况假设" |
| **单写者限定** | 多写者语义需叠加排序组件（论文认为可行） |

### 我读出的额外边界

1. **单 AZ 部署只保证持久，不保证 AZ 级可用**。论文的措辞是"数据仍然持久，故障恢复后可继续服务"——**这意味着 RTO 不可控**，要看 AZ 什么时候恢复。这跟"HA"是两回事。

2. **多 AZ 需要 6 节点才能容忍 AZ+1**，这把成本翻了一倍。论文用分层复制砍掉一半跨 AZ 流量费，但节点成本翻倍仍在。

3. **"对象存储被视为可靠组件"是个强假设**。它把 S3 的可用性与持久性当成了公理（99.99% / 11 个 9）。如果 S3 出区域级故障，BtrLog 的冷读与归档都会受影响——不过热尾仍在 SSD 上，这部分设计是稳健的。

4. **与"日志即数据库"（Aurora）是不同层次的方案**。Aurora 让存储层理解 redo，**连数据页都不传**；BtrLog 只是把日志搬了个地方，数据页仍然照常写。所以 BtrLog 的收益是"日志延迟降低"，不是"网络流量减少"。二者可以叠加，但不是替代关系。

5. **内存约束真实存在**：峰值时每条日志平均 32 MiB，2186 条日志 = 71 GiB。多租户大规模部署时，**内存会成为可服务日志数的硬约束**。

6. **UDP 的选择在高丢包网络下的表现未充分评估**。论文说"Quorum 协议替代了 TCP 的多数保证"，但丢包会触发 resubmit，在拥塞网络下可能放大延迟。论文的评估环境是分区置放群组内的低丢包网络。

## Misc

### 术语表

| 术语 | 含义 |
|------|------|
| **WAL / ARIES** | 预写日志；`append`/`sync`/`scan`/`read` 四操作 |
| **LSN** | Log Sequence Number，单调递增的日志序号 |
| **cLSN** | 最后已提交 LSN（提交水位线），用于读者区分已提交/未提交 |
| **nLSN** | 下一条记录的 LSN |
| **wtoken** | 写令牌，单调递增；同时用作 fencing 与 epoch |
| **Quorum（Qw）** | 写仲裁数，如 2/3、4/6 |
| **staging layer** | 暂存层，SSD 日志节点集群 |
| **segment** | 日志段（如 16 MB），写满后刷到 S3 |
| **prefix sum** | 段内记录字节偏移的前缀和，用于构造字节级一致的段 |
| **fencing** | 写者防护，防止脑裂 |
| **AZ+1** | AZ 整体故障 + 另一个独立故障 |
| **out-of-place write** | 非原地写，避免覆盖旧数据 |
| **deferred eviction** | 延迟驱逐，靠 LSN 窗口保证热数据不被刷走 |

### 易混淆概念

| 对比 | 说明 |
|------|------|
| **durable vs committed** | **对象存储里的数据只是 durable，不一定是 committed**。这是 BtrLog 读路径的核心不变量 |
| **单写者 vs 多写者** | 单写者 ⇒ 排序下放到客户端 ⇒ 单往返；多写者 ⇒ 需要 sequencer ⇒ 至少 2 RTT |
| **急切排序 vs 惰性排序** | Corfu/Scalog 急切（要等排序完成才返回 LSN）；LazyLog 惰性（快但与 ARIES 不兼容） |
| **BtrLog vs Aurora** | BtrLog 是**日志服务**（WAL 换个地方写）；Aurora 是**存储层理解 redo**（连数据页都不传）。层次不同，可叠加 |
| **EBS vs S3** | EBS 中等延迟 + 预配置成本；S3 高延迟 + 按次成本 + 极低容量成本 |

### 一句话总结

> **云上 WAL 的本质矛盾是：块存储太慢太贵，对象存储太慢但极便宜，专有日志后端虽好却不可复用。BtrLog 的答案是分层——用 SSD Quorum 扛住 70 µs 的热尾追加，用对象存储扛住 16 MB 批量的冷归档，中间用"单写者"这个数据库天然满足的假设省掉整个排序层。**

- Kuschewski, Nguyen, Jasny, Ziegler, Leis, El-Hindi. *BtrLog: Low-Latency Logging for Cloud Database Systems*. **PVLDB 19(10): 2894-2907, 2026**. doi:10.14778/3828612.3828640
- arXiv 预印本：https://arxiv.org/abs/2606.27051
- 代码与复现包：https://github.com/maxi-k/btrlog

**论文中重点对比的系统**

- Balakrishnan et al. *CORFU: A Shared Log Design for Flash Clusters*. **NSDI 2012**. （共享日志，链式复制，6 跳；4 KB append ~650 µs，32 盘集群瓶颈 ~180K/s）
- Balakrishnan et al. *CORFU: A distributed shared log*. ACM TOCS 31(4), 2013.
- Ding et al. *Scalog: Seamless Reconfiguration and Total Order in a Scalable Shared Log*. **NSDI 2020**. （排序与存储解耦；~1.6 ms，原型 255K 全序/s）
- *LazyLog*. （惰性排序，单往返但不返回 LSN，与 ARIES 不兼容）
- Apache BookKeeper. （单写者 + 客户端驱动 Quorum；为 HDD 时代设计）
- Balakrishnan et al. *Virtual Consensus in Delos*. **OSDI 2020**.
- Bhat et al. *Low End-to-End Latency atop a Speculative Shared Log with Fix-Ante Ordering*. **OSDI 2025**. （SpecLog）
- Lockerman et al. *FuzzyLog*. **OSDI 2018**. （偏序换并发）
- Bernstein, Reid, Das. *Hyder - A Transactional Record Manager for Shared Flash*. **CIDR 2011**. （思想源头）

**云存储与延迟实测**

- Bodner, Radig, Justen, Ritter, Rabl. *An Empirical Evaluation of Serverless Cloud Infrastructure for Large-Scale Data Processing*. **EDBT 2025**. （论文引用 [18]，对象存储写延迟"数十毫秒"的实证来源）
- Verbitski et al. *Amazon Aurora: Design Considerations for High Throughput Cloud-Native Relational Databases*. **SIGMOD 2017**.
- Antonopoulos et al. *Socrates: The New SQL Server in the Cloud*. **SIGMOD 2019**. （XLOG）
- *Amazon EBS User Guide → Volume Types*. （io2 / gp3 规格与定价，成本计算依据）
- Axboe. *Efficient IO with io_uring*. （BtrLog 自研运行时基础）
